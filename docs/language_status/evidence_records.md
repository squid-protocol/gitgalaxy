# Evidence records: what a ported program's proof claims, and who accepted it (#4048)

Each ported program has one **evidence record**: a JSON file committed beside the port. It is the unit a customer
receives next to the Java. It gathers what is otherwise spread over a proof's work directory, the coverage report,
the porting loop's provenance and the mutation scores, and it says whether all of that is still current.

| port | record | rendered page |
|---|---|---|
| equivalence case | `tests/equivalence/<case>/evidence.json` | `docs/language_status/evidence/<case>.md` |
| CICS crucible port | `tests/cics_crucible/ports/<case>/<PROGRAM>/evidence.json` | `docs/language_status/evidence/crucible-<case>-<PROGRAM>.md` |

The index of every record is [`evidence/README.md`](evidence/README.md). The pages are generated by
`python tests/tools/evidence.py render`; never edit them by hand.

## What a record holds (`gitgalaxy-evidence/1`)

- **The claim.** It is rendered from the numbers, never typed: runs and fault runs, records compared, COBOL
  paragraph and branch coverage, the mutation score (raw and adjusted, with every survivor triaged), and the
  methods no proof runs.
- **The proof.** The verdict, per-output counts, the harness commit, and the digest of the inputs it ran against.
  The diffs themselves stay in the run's `report.json`, so a record holds no data records.
- **The inputs it was proven against.** Each input is a sha256 tree digest: `path \0 bytes \0` over sorted
  repo-relative paths.
  - `port`: the port, plus any port its proof also lays.
  - `case`: `case.json` and its `@case/` inputs.
  - `corpus`: the corpus pin. For a crucible port, this is the cics-crucible pin.
  - `differences`: the declared differences (#4051; none yet).
  - `harness`: the equivalence and crucible tools.
  - `oracle`: the GnuCOBOL Dockerfiles and the CICS, LE, fault and SQL models.
  - `generator`: `gitgalaxy/tools/cobol_to_java/**`.
- **The oracle.** For equivalence ports this is GnuCOBOL plus the harness's models, with the fingerprint of the
  image the proof ran on: `cobc --version`, the Debian package, the image id and whether it matches the pin (#4309).
  For crucible ports it is the crucible's hand-written expected logs.
- **Reach (#4255).** Every method of the port that no proof runs, sorted into three kinds:
  - **stub**: the generator's placeholder, kept;
  - **left as generated**: the generated body, unchanged;
  - **ported_unproven**: behaviour the port added that no proof runs.

  The proof runs a port through runTask, handleCall or runBatch. A batch case may also list `entries`: no-argument
  methods of the service, such as a controller's `executeX`. Each one gets an **entry run**: the step runs once
  more through that method and is compared with the same COBOL run. The method returns no RETURN-CODE, so the
  run counts as RETURN-CODE 0 when it returns normally. Only a method that an entry run actually ran counts as
  reached.

  **Which entry points "proven" covers (#4343).** A CICS crucible port is proven through two paths, and both must
  pass every scenario of its program. The first is runTask: the harness builds each task and calls it (the
  `java-ported` side). The second is the port's deployed entry points, the Spring facades a deployment calls: the
  harness enters each task through the program's `handleTransaction`, and every program a LINK or XCTL reaches
  through its `handleLink`, with the scenario's region joined (`CicsTask.join`) so the facade's task is the
  scenario's own (the `java-facade` side). A facade that builds a task of its own, or does not run its task in the
  region, fails the scenario. The record's `entry_points` (and `proof.entry_runs`) name the facades the passing
  scenarios actually entered by; a facade no scenario enters by (for example the `handleLink` of a program no
  scenario LINKs to) is not counted as reached. The equivalence cases (CardDemo, GenApp, CBSA) are still proven
  through runTask / handleCall / runBatch only.
- **Mutation (#4047).** The port's entry of `mutation_scores.json`, with the inputs it was judged against
  (recomputed at its commit from git history).
- **Provenance.** Who or what wrote the port: the model, backend, attempt and ticket hash, citing the loop's
  `provenance.json` by path and hash. For a hand port, the person and first commit from git.
- **Approvals.** Append-only. Only a person writes them (see [Approval](#approval-a-named-person-takes-responsibility)).

## Status is computed, never stored

Nothing in a record says "proven". `python tests/tools/evidence.py status` recomputes every input digest from the
tree and compares it with the record's. It returns a status and every reason for it:

| status | when |
|---|---|
| `not-proven` | No proof, a proof that failed, **or a ported_unproven method** (below). |
| `stale` | Any input has changed since the proof. A stale record is never shown as proven. |
| `proven, unapproved` | The proof is current, and no current approval exists. |
| `proven, approved` | The latest approval was made against the record's current inputs. |

**Which staleness fails CI** (owner decision, #4048 Q1):
- A change to a port, its case, its corpus pin or its declared differences fails
  `tests/cobol_mainframe/test_evidence.py`. The PR that makes the change re-proves the record:
  `python tests/tools/evidence.py prove KEY`, or `equivalence.py run CASE --record`.
- A change to the harness, the oracle or the generator stales every record at once. Those records show as stale,
  and the nightly [Evidence Refresh](../../.github/workflows/evidence-refresh.yml) job re-proves them
  (`evidence.py refresh --stale`, also on `workflow_dispatch`). It opens a draft PR with the refreshed records.

**Unproven methods** (owner decision, #4048 Q7): under the policy switch
`PORTED_UNPROVEN_POLICY = "block"` in `tests/tools/evidence.py`, a port with any ported_unproven method is **not
proven**. Its status says why, for example "1 ported_unproven method (executeCsutldtc)". To become proven, the
method is either removed from the port or reached by a proof. Stubs and left-as-generated methods are counted and
never block. Setting the switch to `"report"` turns ported_unproven into counts only, with no change to any record.

The rendered pages judge each record on its own contents (verdict, policy, approvals), so they do not change when
the tree moves. Staleness is always computed live.

## Approval: a named person takes responsibility

The sign-off is **accountability, not COBOL expertise**. The approver attests to one sentence, stored verbatim in
the record together with the rendered claim they saw and the inputs digest it covers:

> I reviewed this evidence summary (scenarios run, coverage, unproven methods, declared differences) and accept it
> for *&lt;purpose&gt;*.

This is what an industry partner needs: a named person, not a model, took responsibility for accepting this
evidence for a stated purpose.

```
python tests/tools/evidence.py approve carddemo-dateutil --by "Jane Reviewer" --for "the Q4 pilot cut-over"
python tests/tools/evidence.py reject  carddemo-dateutil --by "Jane Reviewer" --for "..." --note "why"
```

**When `approve` refuses.** It refuses in each of these cases:
- the record is not `proven` and current (re-prove it first);
- stdin or stdout is not a terminal (a script, a CI job or an agent harness);
- `--by` names a tool or a model;
- `--for` is empty;
- the person does not retype the name given to `--by` to sign.

An approval covers the inputs digest it was made against. Any later change to an input makes it "approved for an
earlier version", shown as not approved.

**Tools never write approvals.** `test_no_tool_writes_an_approval` fails in either of these cases:
- any tool or engine file other than `evidence.py` names the `approvals` key;
- a write to it inside `evidence.py` happens outside `_append_approval`.

Every tool that rewrites a record keeps the approvals on disk byte for byte.

## Who writes what

| writer | sections |
|---|---|
| `equivalence.py run CASE --record` (committed port, committed case, no overrides) | inputs, proof, coverage, reach, oracle, provenance, mutation |
| `evidence.py prove KEY` / `refresh --stale` (crucible ports through `cics_crucible.py --report-dir`) | the same |
| `mutation_scores.py build` (into the committed file) / `evidence.py mutation` | mutation |
| `evidence.py approve` / `reject` (a person at a terminal) | approvals |

## Defaults taken when the record was built (the owner may revisit)

These follow the #4048 proposal's recommendations:
- **Q2, the generator fingerprint**, covers `gitgalaxy/tools/cobol_to_java/**`, not the whole engine.
- **Q3, the mutation score** goes stale on port, case, corpus, harness or oracle changes, not on the generator. Only
  a mutation run, or a re-judged one, refreshes it. A re-proof does not.
- **Q4, crucible ports** get a new `evidence.json` beside `provenance.json`. `cics-crucible-port/1` stays as the
  loop's log, re-stamped at each pin bump (#4308).
- **Q6, hand ports**: `written_by: "person"`, with the author and first commit taken from git.
- **Q8, coverage**: numbers only, with no threshold policy.
- **Q9, the oracle**: the image is pinned (#4309). The image id is recorded but is not part of the digest; the
  Dockerfile pin is.
- **Q10, customer projects** (`ai_agent_jobs/ports/<KEY>/evidence.json`): not in v1.
- **Corpus and crucible pins** count with the case, so changing them blocks the PR.
