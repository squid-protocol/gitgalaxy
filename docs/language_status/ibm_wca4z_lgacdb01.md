# IBM watsonx Code Assistant for Z's LGACDB01 translation, through our equivalence harness

Run 2026-10-02 with `tests/tools/ibm_wca4z_port.py`. This is the detailed record. The comparison of the four
LGACDB01 files (stock COBOL, IBM's refactored COBOL, IBM's Java, our det port) is in
`docs/research/lgacdb01-four-way.md`.

## What IBM published

IBM Research's validation papers (arXiv [2506.10999](https://arxiv.org/abs/2506.10999), ASE 2024, and
[2504.10548](https://arxiv.org/abs/2504.10548)) validate WCA4Z translations one COBOL paragraph at a time. For one
program, GenApp's LGACDB01, they published the inputs and outputs at
[sandeephans/validation-c2j](https://github.com/sandeephans/validation-c2j). We use its only commit, `967d00b`
(2024-10-11). It contains:

- `LGACDB01.cbl`: the program as WCA4Z's Refactoring Assistant extracted it ("Generated by: IBM watsonx Code
  Assistant for Z Refactoring Assistant"), 418 lines. Stock GenApp's `lgacdb01.cbl` is 328 lines.
- `generated_code/java`: the WCA4Z Java. `Lgacdb01.insertCustomer` is the translated paragraph. The 21 data classes
  around it map record layouts through IBM's JZOS field API.
- `generated_code/test`: the generated JUnit test (PowerMock, mocked JDBC), with the COBOL test data it asserts
  against.
- `generated_code/cache/Lgacdb01.insertCustomer.json`: a recorded run of that test.

The repository has no license, so nothing from it is committed here. The runner fetches it at the pinned commit,
and this document quotes a few lines.

### IBM's method, as the papers describe it
- One paragraph per program is selected, the one with the most resource access. For LGACDB01 that is
  INSERT-CUSTOMER.
- Its paths are enumerated by symbolic execution.
- The COBOL tests run on a real z/OS mainframe, with resource access handled by a debugger script.
- The recorded program and resource outputs become JUnit assertions against the Java, with the database calls
  mocked.
- The papers report 4/4 tests passing for LGACDB01's INSERT-CUSTOMER and 100% path and branch coverage of that
  paragraph.

### The refactored COBOL against stock GenApp
- **INSERT-CUSTOMER is the stock paragraph.** Ignoring comments, blank lines and the sequence area, the text is
  identical.
- **The data it reads and writes has the same layout on the success path:**
  - the CA-* fields (the same LGCMAREA copybook, here as `DFHCOMMAREA-1`);
  - `DB2-CUSTOMERNUM-INT PIC S9(9) COMP`;
  - `LGAC-NCS PIC X(2) VALUE 'ON'`;
  - `EM-SQLREQ`.
- **One difference, on the error path only.** The refactored ERROR-MSG gains `' PNUM='` and `EM-POLNUM PIC X(10)`,
  16 bytes stock LGACDB01 does not have. WRITE-ERROR-MESSAGE also reads `DFHCOMMAREA-1` rather than the LINKAGE
  `DFHCOMMAREA`.
- **The refactored program is a unit-test target, not a CICS program.**
  - It has no mainline: the PROCEDURE DIVISION starts at INSERT-CUSTOMER.
  - Its COMMAREA is in WORKING-STORAGE, so a caller's COMMAREA never reaches it.
  - INSERT-CUSTOMER ends in `EXIT.` with no GOBACK, so every run falls through into WRITE-ERROR-MESSAGE.
  - IBM's tool supplies the inputs through a debugger.

## Our method

`equivalence.py` runs the genapp-lgacdb01 case. That is the stock program and the programs it LINKs (LGACVS01,
LGACDB02), 4 scenarios. Each scenario is one CICS task, run twice:
- the COBOL under GnuCOBOL and our CICS model, against IBM Db2 Community Edition;
- the Java port against the same Db2.

After each scenario the harness compares, byte for byte, the CUSTOMER and CUSTOMER_SECURE tables, the KSDSCUST
VSAM file, the returned COMMAREA and the CICS events (LINKs and returns). No resource is mocked.

### The port proven here: IBM's paragraph inside our det port
- **IBM's code is fetched unmodified.** `Lgacdb01.insertCustomer` and the classes it uses, byte for byte.
- **Our code, proven equivalent on its own:**
  - the det port of the genapp-lgacdb01 case (`det_port.py --translate-only`), which covers LGACDB01's other
    paragraphs (MAINLINE, OBTAIN-CUSTOMER-NUMBER, WRITE-ERROR-MESSAGE);
  - the det ports of LGACVS01 and LGACDB02.

  So IBM is judged on the paragraph WCA4Z translated, and not on paragraphs it never claimed to translate.
- **The adapter (ours, `tests/tools/ibm_wca4z`)** has three parts.
  1. *The paragraph swap.* The det method for INSERT-CUSTOMER becomes a call that:
     - builds IBM's `CaCustomerRequest` and `Genasa1Customer` from the paragraph's host variables (CA-FIRST-NAME …
       CA-EMAIL-ADDRESS as the COBOL holds them; CA-DOB as `java.sql.Date`, which IBM's model declares);
     - calls `insertCustomer(DB2-CUSTOMERNUM-INT, LGAC-NCS, request)`;
     - stores `request.getCaCustomerNum()` back into DB2-CUSTOMERNUM-INT and CA-CUSTOMER-NUM. IBM's method reports
       the number only that way: its `db2CustomernumInt` is a value parameter. Reading it back as both fields is
       the charitable choice, since the COBOL paragraph ends with the two equal.
  2. *The connection.* IBM's code connects with `DriverManager.getConnection("endpoint_url")`. A JDBC `Driver`
     registered for exactly that URL answers with a proxy of the task's own transaction-bound Db2 connection, whose
     `close()` does nothing. IBM's INSERT then runs in the same unit of work and schema as the rest of the task. We
     chose a driver over a classpath shim of `DriverManager` because it leaves the JDK alone and is visible in one
     class.
  3. *A JZOS compile shim.* IBM's classes reference `com.ibm.jzos.fields`, which ships only with IBM's Java for z/OS.
     The shim keeps JZOS's field-offset bookkeeping, which IBM's static initialisers run, and throws on every byte
     conversion. The adapter never converts bytes, so no shim behaviour can reach a result.

## Results

### Against stock LGACDB01 (the case's reference)
**Not proven.** On every scenario, IBM's INSERT is refused by the Db2 driver before it reaches the database.

| Scenario | Stock COBOL (reference) | IBM's INSERT-CUSTOMER in the task |
|---|---|---|
| add-with-counter (`LGAC-NCS = 'ON'`) | '00'; CUSTOMER row 1000011 with DATEOFBIRTH 1815-12-10; CUSTOMER_SECURE row; VSAM copy | `-4461`: "Invalid parameter 4: Parameter is not set nor registered", printed and swallowed; no CUSTOMER row; the task continues |
| add-without-counter (DEFAULT key) | '00'; CUSTOMER row 1000001 (identity), CA-CUSTOMER-NUM 1000001 | `-4461` on parameter 3; no row; CA-CUSTOMER-NUM 0, because the generated key is never read |
| add-blank-optional-fields | '00'; CUSTOMER row 1000020 | `-4461` on parameter 4; no row |
| add-long-email | '00'; CUSTOMER row 1000030 | `-4461` on parameter 4; no row |

In every scenario the task then runs on as if the INSERT had worked:
- LGACVS01 writes the VSAM copy.
- LGACDB02's CUSTOMER_SECURE insert breaks its foreign key (`FOREIGN KEY(customerNumber) REFERENCES customer`),
  because the CUSTOMER row is missing.
- LGACDB02 takes its error path: WRITE-ERROR-MESSAGE, then `LINK LGSTSQ`.
- GenApp's error logging through LGSTSQ is refused by name (register X6), so the harness stops the Java side there.

The CUSTOMER table difference, a missing row, is established when IBM's statement fails; everything after it follows
from that.

### Against IBM's refactored LGACDB01: not run
Its INSERT-CUSTOMER is the stock paragraph, with the same data layouts on the success path, so the scenarios above
already test exactly the paragraph IBM translated. As a reference program of its own it cannot be judged:
- a CICS COMMAREA does not reach its WORKING-STORAGE `DFHCOMMAREA-1`;
- every run falls through into WRITE-ERROR-MESSAGE and its `LINK LGSTSQ`, refused by X6, whatever the port does.

### Root causes in IBM's Java (`Lgacdb01.java` at `967d00b`)
1. **DATEOFBIRTH is never bound.** In both INSERT branches the binding is commented out, while the SQL text still
   names the column and its `?`:
   `// ps.setDate(4, caCustomerRequest.getGenasa1Customer().getDateofbirth());` (and `ps.setDate(3, …)` in the
   DEFAULT-key branch). Db2's driver refuses a statement with an unset parameter (-4461), so no row is ever written.
   A driver that accepted it would store a NULL or default DATEOFBIRTH, which is still a difference from the
   COBOL's `:CA-DOB`.
2. **A failed INSERT is swallowed.** The COBOL's `MOVE '90' TO CA-RETURN-CODE`, `PERFORM WRITE-ERROR-MESSAGE` and
   `EXEC CICS RETURN` became `// caReturnCode = 90;`, `// errorMsg.writeErrorMessage();` and
   `System.out.println("[EXCEPTION CAUGHT] " + exception);`. The paragraph returns normally, and the program goes
   on to LINK LGACVS01 and LGACDB02 with no customer row. This path was exercised in every scenario.
3. **The DEFAULT-key branch loses the key.** On failure `db2CustomernumInt` stays 0, which is also the value
   `setCaCustomerNum` reports (add-without-counter: CA-CUSTOMER-NUM 0 against 1000001). On success the key would come
   from `getGeneratedKeys()` rather than the COBOL's `IDENTITY_VAL_LOCAL()`, which return the same value for a
   single-row INSERT.
4. **`equals(Lgacdb01)` returns `true` unconditionally.** This is confirmed in the code, but nothing in either run
   calls it, so it has no effect on these results.

### IBM's own JUnit test
- **It does not compile against the published Java.** It calls `lgacdb01Obj.insertCustomer()` with no arguments
  (test lines 133 and 231), but `insertCustomer` is `static void insertCustomer(long, String, CaCustomerRequest)`.
  The Java's commented-out locals (`// CaCustomerRequest caCustomerRequest = new CaCustomerRequest();`,
  `// long db2CustomernumInt = 0;`, `// String lgacNcs = "ON";`) suggest the method was a no-argument one when the
  test was generated, and was changed afterwards.
- **The recorded run in the repository is 2 passes and 2 failures:**
  - tests 1 and 3 have empty bodies ("Skipping this test, since there is a cobol_resource_input with var =
    "SQLCODE OF SQLCA" with non-zero value"), so they pass trivially;
  - tests 2 and 4 fail with `expected:<[xxxxxxxx]> but was:<[]>` (CUSTOMER.POSTCODE).
- **The papers report 4/4 for LGACDB01.** The published artifacts do not reproduce that. They may be from a different
  snapshot than the papers measured, and we cannot tell which.
- **If it compiled, it would probably catch the DATEOFBIRTH defect.** It asserts `CUSTOMER.DATEOFBIRTH` from the
  `setDate` mock, which is never called. A mock does accept a statement with an unset parameter, so the driver's
  refusal, and what follows it in the rest of the task, would not appear.

### Found in our own port
IBM's swallowed failure drove the task into GenApp's error path, which none of our proven scenarios had reached.
There our det port of LGACDB02 crashed:
- `LINK LGSTSQ COMMAREA(ERROR-MSG)`, 71 bytes, is marshalled with the DTO of CA-ERROR-MSG (`FILLER X(9)`,
  `CA-DATA X(90)`), so it reads past the record:
  `StringIndexOutOfBoundsException: offset 9, count 90, length 71` in `fill_Lgacdb01CaErrorMsg`.
- LGACDB01's det port has the same code on its own error path.
- This is a det-port defect, not IBM's, and it is invisible to every proof we have because we never inject SQL
  failures (register M2; #4173).
- The runner's `--clamp-error-msg` works around it in its scratch copy only, so the diagnostic runs above could reach
  the LGSTSQ refusal. The primary run, without the flag, stops at this crash.

## What each method catches

| | IBM (paragraph, mocked resources, z/OS reference) | Ours (whole task, real Db2 and CICS model, GnuCOBOL reference) |
|---|---|---|
| Binding missing from a statement | Yes, through the parameter mock's assertion, if the test compiles | Yes: the driver refuses it, or the table differs |
| What a failure does to the rest of the program | No: one paragraph, and mocks do not fail | Yes, up to a refused construct (here X6, LGSTSQ) |
| Error paths | Yes, from symbolic paths with non-zero SQLCODE inputs (skipped for LGACDB01's two such tests) | Only if a scenario reaches them; no SQL fault injection yet (#4173) |
| Reference fidelity | Real z/OS | GnuCOBOL; see `oracle_assumptions.md` |
| Coverage | 100% of one paragraph's branches | The whole program; LGACDB01 det: 6/14 branches. Solver-driven scenarios (#4175) would lift this |

## Limits of this comparison
- **One program, one paragraph, one published snapshot.** The Java at `967d00b` may not be what the papers measured.
- **The adapter is ours.** Its choices, chiefly reading the customer number back through `caCustomerRequest`, are
  documented above. A different choice there cannot change the outcome, which is decided when IBM's INSERT is
  refused.
- **The reference is GnuCOBOL with our CICS model, not z/OS.** The difference found here (an INSERT that writes no
  row) does not depend on any assumption in the register.
- **The refactored COBOL is not run as a reference,** for the reasons above.

## Reproducing
```sh
# environment: .claude/skills/det-port/SKILL.md (JAVA_HOME, GITGALAXY_MAINFRAME_CORPORA, license key, Db2 container)
python tests/tools/ibm_wca4z_port.py --work /tmp/ibm --junit              # primary run, plus IBM's JUnit
python tests/tools/ibm_wca4z_port.py --work /tmp/ibm --clamp-error-msg \
    --scenario add-without-counter                                         # diagnostic, one scenario
```
`DIR/result.json` has the verdict lines. The swallowed exception is in
`DIR/proof/java/java_h2/target/surefire-reports/*.xml`, and `DIR/ibm-junit.log` has IBM's test build.
