title: "COMP-5 byte order — DIFFERS; byte uses refused by name"
area: "compiler"
summary: "COMP-5 byte order: little-endian vs z/OS big-endian"
reached: "read as numbers only (a VALUE beyond the PICTURE: fixed, #4501)"
---
- **What.** GnuCOBOL stores COMP-5 in the machine's order, little-endian on x86; z/OS is big-endian. COMP, COMP-4
  and BINARY are big-endian on both.
- **Visible only** when a COMP-5 item's bytes are read as bytes: a REDEFINES, a group MOVE, or a record written to a
  file.
- **Reached.** The harness's SQLCA declares its binary fields COMP-5, as IBM's does, and programs read them only as
  numbers. In the corpora, only CardDemo's IMSFUNCS.cpy declares COMP-5.
- **A VALUE beyond the PICTURE (#4501, fixed).** COMP-5 holds up to its 2, 4 or 8 bytes' capacity, not the value
  its 9s imply. The det translator wrote a COMP-5 VALUE truncated to the PICTURE and big-endian while its runtime
  reads COMP-5 little-endian: `S9(4) COMP-5 VALUE 32767` read back as -12534 (cics-crucible `ca-xctl-versions`,
  XCTL LENGTH). The image now holds the whole value in the runtime's (GnuCOBOL's) order; pinned by
  `test_det_programs.py` COMP5 against GnuCOBOL.
- **Refused by name (#4271).** The det translator no longer proves a program on the oracle's byte order: a COMP-5 item
  of 2 or more bytes whose bytes are observed -- a group holding it used as a whole (MOVE, compare, 88), a REDEFINES
  over it by a non-COMP-5 item, a reference modification of it -- is a Hole ("COMP-5 is little-endian on the oracle,
  big-endian on z/OS: oracle_assumptions.md C7"), through the guard COMP-1 / COMP-2 use (`Gen.overlaps_float`,
  `comp5_extents`). Read as a number it is translated as before. Pinned by `test_det_programs.py`
  `test_comp5_bytes_are_refused_by_name_where_the_oracle_and_zos_differ`. `det_port.py check`: no committed port moved
  (119 of 119 unchanged), so no burned program observes COMP-5 bytes.
  - **File and sort records (#4271).** A record is named by its FD, so READ, WRITE, REWRITE, SORT USING / GIVING and
    RETURN reached its bytes without `field_expr`'s guard. `Gen.check_record_bytes` now refuses a record holding a
    COMP-5 item of 2 or more bytes (and, for C6, a COMP-1 / COMP-2 item) by name; pinned by `test_det_programs.py`
    `test_record_io_*`.
  - **Not covered (sibling gaps):** the SQLCA record (the SQL lane hands the whole group to the runtime, which sets
    its COMP-5 fields as numbers; a program that MOVEs the SQLCA as bytes is not refused); an elementary COMP-5 item
    passed BY REFERENCE to a CALLed program or in a COMMAREA (the callee reads the oracle's order); INITIALIZE and
    group VALUE images, which write numbers. Burned estates reading COMP-5 as numbers only: CardDemo
    `IMSFUNCS.cpy`, cics-async `SEQPNT` / `ASYNCPNT`, DBB `EPSCSMRD`.
- **Sharper refusal text (#7646).** The overlap Hole now says how the bytes are covered: "its bytes hold FV COMP-5, as a
  group holding it" or "..., as a REDEFINES overlay of the same storage" (`Gen.overlap_how`; same for COMP-1 / COMP-2,
  C6). Wording only: no program's translation moved. Pinned by `test_det_programs.py`
  `test_overlap_refusal_names_the_item_and_how_it_overlaps` (synthetic data, all three usages x both shapes). Modelling
  the byte view itself (z/OS big-endian COMP-5, HFP COMP-1 / COMP-2 bytes) stays a Remaining slice: the oracle's bytes
  differ, so it needs a declared comparator difference, not a loosened proof.
- **The z/OS byte image (#7646 slice 1; the runtime only).** `Cobol.swapZosComp5(true)` holds every COMP-5 item
  big-endian, two's complement over its 2, 4 or 8 bytes, as z/OS does (`Codec.littleEndian`); off (the default) keeps
  the oracle's little-endian image, so no port moved. Same value, capacity and truncation either way: only the byte
  order. **Declared comparator difference:** the oracle's bytes for a COMP-5 item are the z/OS bytes reversed, nothing
  else -- measured on GnuCOBOL 3.1.2 (2026-11-04) for S9(4), S9(9) and S9(17); a proof that observes COMP-5 bytes may
  state exactly that and no more. Pinned both ways (synthetic values, IBM's layout written by hand) by
  `test_det_programs.py` `test_comp5_zos_byte_order_*`. Wired in slice 2 (#7646): `det.program.translate(zos_comp5=True)` writes the VALUE image
  big-endian, wraps every entry in `Cobol.swapZosComp5(true)` (restored after), and lifts the refusals above (group
  MOVE, REDEFINES, reference modification, record bytes, 88 on an overlaid item) because the byte image is then IBM's,
  not the oracle's. Default off: no port moves. An LE / Db2 service (`Dsntiac`, `CEE*`), a CALL outside its source or a CICS
  LINK / XCTL whose COMMAREA covers a COMP-5 item stays refused under the switch, by name (`program.zos_comp5_refusal`):
  those COMP-5 bytes are the runtime's, little-endian. (Slice 2 refused all EXEC SQL and every LINK / XCTL COMMAREA;
  #7709 slice 5b lifted both, see below.)
  **IMS DL/I (slice 4):** `CALL 'CBLTDLI'` / `'CEETDLI'` is not a foreign program: `DetDli` moves the I/O area's bytes as
  held (it reads no COMP-5 itself), so the area is IBM's big-endian image under the switch, as IMS expects. `AIBTDLI`
  and a program IMS does not enter at `DLITCBL` stay refused by name. CardDemo PAUDBLOD, PAUDBUNL and DBUNLDGS
  translate whole under the switch and are proved under a declared `comp5_byte_order` (the IMS `diff_db` / `diff_gsam`
  reversal landed in #7734). Pinned by `test_det_zos_comp5.py`.

- **The declared comparator difference (#7646 slice 3).** A case may carry `"declared_differences": ["comp5_byte_order"]`
  (`equivalence_common.declared_differences`; an unknown or repeated kind is refused by name). `diff_records` then reads
  each COMP-5 field of 2 or more bytes of the ORACLE record reversed, i.e. as z/OS holds it, and compares it with the
  port's bytes: every other byte, every other usage (COMP is big-endian on both) and the port side are compared as before,
  so a port still holding the little-endian image, or a real value difference, stays a difference. The declaration is
  written to the evidence record as a difference of kind `declared` (replaced by every proof, as `option` ones are).
  Pinned by `tests/tools/test_equivalence_declared_differences.py`. The same reversal is now at the
  variable-record and CALL comparators (#7729), the CICS-file comparator (#7733), the IMS comparators (#7734) and the
  CICS oracle COMMAREA read (#7740). Still to land: the HFP byte view for COMP-1 / COMP-2.
- **The default is the z/OS order (#7646 slice 5, #7709; owner ruling B).** `det.program.translate()` holds COMP-5
  big-endian unless told `zos_comp5=False` (the GnuCOBOL-native what-if). Left at the default it acts only on a program
  that holds a COMP-5 item of 2+ bytes outside the SQLCA: such a program gets the `swapZosComp5` wrapper and the refusals
  below; a program without one (GenApp, most of CBSA) is translated as before, byte for byte, even when it uses SQL or a
  foreign CALL. A program that holds COMP-5 and meets one of the refusals below (a foreign CALL, a LINK / XCTL
  COMMAREA over a COMP-5 item) cannot be held big-endian, because those bytes are the runtime's; under the default it
  keeps the oracle's order as before, and an explicit `zos_comp5=True` refuses it. That is a gap against "every
  program" (a sibling gap, #7709). zECS zecs001 / zecs002 / zecsnc hold COMP-5 in their
  copybooks and were re-ported (and re-proved) under the switch. An explicit `zos_comp5=True` acts on every program. `det_port.port_case` and `equivalence_java` no longer
  read the case: `comp5_byte_order` stays in `declared_differences` as the comparator's reading of the oracle's
  reversed bytes only. CardDemo PAUDBLOD, PAUDBUNL and DBUNLDGS (`CALL 'CBLTDLI'`, no SQL / LE / foreign CALL) keep
  translating whole; their only COMP-5 item is IMSFUNCS `PARMCOUNT`, read by no CALL. Pinned by
  `tests/tools/test_det_port_zos_comp5_7646.py`.
- **The async pair (#7646, #7750).** CICS-async ASYNCPNT and SEQPNT declare `comp5_byte_order` and are ported and proved
  under the switch. Their `PUT` / `GET CONTAINER` areas cover no COMP-5 item, so the refusal, which is now narrowed to
  an area that covers one (`program._container_comp5`; before, every LINK with a channel), does not reach them. Each
  carries 8 `swapZosComp5` restore survivors, tracked in #7756.
- **EXEC SQL and the LINK / XCTL COMMAREA (#7709, PR #7841).** The SQLCA follows the order: `DetSql.putInt` and the
  WHENEVER read write and read its COMP-5 fields big-endian under the switch, so EXEC SQL is no longer a refusal. A
  LINK / XCTL is judged by its COMMAREA area, as a channel's containers are (`program._COMMAREA_AREA`,
  `_container_comp5`): an area covering no COMP-5 item of 2+ bytes hands over no COMP-5 byte and translates; one that
  covers one is refused ("LINK / XCTL COMMAREA: ..."). CBSA BNK1TFN and XFRFUN translate whole under the switch; the
  cruc-ca-xctl-versions front CAXA (its only COMP-5 item, `WS-BIGLEN`, is the LENGTH operand; the areas `WS-V1` and
  `WS-BIG` hold none) takes the `swapZosComp5` wrapper under the default, checked 2026-11-05 (default and `True` wrapped,
  `False` not). The committed cics-crucible ports and det-ports hold no COMP-5 byte view, so none moved. A program
  with no COMP-5 item of 2+ bytes outside the SQLCA keeps the oracle's order, SQL or not. Pinned by
  `test_det_port_zos_comp5_7646.py` and `test_det_zos_comp5.py`. The Db2 and LINK cases' evidence records go stale on
  `DetSql.java` and are re-proved by the evidence refresh, not by hand.
- **Still refused by name under the switch:** LE / Db2 CALLs (`CEE*`, `DSNTIAC`), a CALL outside the source, a LINK /
  XCTL whose COMMAREA covers a COMP-5 item, a container area covering a COMP-5 item, `AIBTDLI`. The default is on (slice
  5 flipped it to on, #7709). Not covered: a MOVE of the SQLCA as bytes; a COMP-5 item passed BY REFERENCE to a CALLed
  program.
- **Slice 5 follow-through (#7709).** Landed with the flip: the default. Done after it: no golden moved (the default acts
  only on a program that holds COMP-5, and `det_port.py check` changed five ports, all re-proved); PAUDBLOD, PAUDBUNL and
  DBUNLDGS are unchanged (L4); ASYNCPNT and SEQPNT stay L5 with every survivor accounted (#7756; the evidence report of
  2026-11-06 lists 0 stale programs in both estates). Still to do: census T3 (#7709), which needs the census clones,
  and the sibling gaps above (#7841 lifted SQL and a COMMAREA over no COMP-5 item; a COMMAREA over one keeps the oracle's order). Their
  `comp5_byte_order` declarations stay: they are the comparator's difference, not a translator switch.
- **The SQLCA read as bytes (#7646 slice 2, 2026-11-06).** A program holding no other COMP-5 item kept the oracle's order
  (the default acts only where one is held, #7709), and the SQLCA's COMP-5 fields followed it, so a read of the SQLCA as
  bytes saw the oracle's order, not z/OS's, with no Hole. CardDemo COTRTUPC does this: `STRING ... SQLERRM OF SQLCA` takes the
  group `SQLERRM`, whose first two bytes are the COMP-5 `SQLERRML`. (COTRTLIC and `carddemo-cotrtlic-generated` do not: their
  `CSDB2RPY.cpy` names SQLERRM only in a comment, and `det_port.py check` shows their ports unchanged.) Refusing by name was tried and dropped (it turns three whole ports into Holes). Now the SQLCA's
  COMP-5 items are tracked (`Gen.sqlca_extents`); a statement whose operand covers one (a group holding it, a REDEFINES,
  a reference modification; not the SQL lane's own hand-off, `Gen.sql_handoff`) sets `Gen.sqlca_bytes`, and the default
  switch repeats that program held big-endian (`program.SqlcaBytesRead`, `SQLCA_HOLD`): wrapper on, SQLCA items in
  `comp5_held`. A program that reads the SQLCA only as numbers or its text (`SQLCODE`, `SQLERRMC`) keeps its port byte for
  byte. `det_port.py check`: 269 of 270 ports unchanged, COTRTUPC gains the wrapper. **Its proof first DIFFERED, by exactly that byte order:** the screen text `screen.ERRMSG` carries SQLERRML (48) as `0\x00` in the oracle and `\x000` in the port (z/OS's order). Now `carddemo-cotrtupc` declares `comp5_byte_order` and the CICS comparator reads the oracle's screen and SEND TEXT text as z/OS holds it (`equivalence_common.comp5_zos_text`): each oracle halfword `n, 0` with n 1 to 70 (SQLERRML's range) reads `0, n`, nothing else, and the port's text is never touched, so a port that kept the oracle's order still differs. The proof reads PROVED again (54 scenarios, every event equal). Pinned by `test_det_zos_comp5.py`.
