- **DFSORT subset (#4268).** `det/dfsort.py` parses a SORT step's SYSIN and SYMNAMES and lowers the step to a COBOL
  SORT program; the oracle runs that program, the port is its det translation, and the SORTOUT bytes are compared
  (`tests/cobol_mainframe/test_dfsort_4268.py`: CardDemo's TRANREPT STEP05R, SORTTEST and COMBTRAN cards, plus COPY /
  OMIT, EQUALS with PD and BI keys, and MERGE with INCLUDE). The lowering is the assumption; **IBM.** z/OS DFSORT
  Application Programming Guide (SC23-6878), "SORT control statement", "MERGE control statement", "INCLUDE control
  statement", "OPTION control statement", "Using symbols for fields and constants":
  - SORT / MERGE FIELDS=(p,m,f,o) with CH (unsigned; compared by EBCDIC bytes as DFSORT does: the step is lowered under an EBCDIC PROGRAM COLLATING SEQUENCE and the port stops by name where the two EBCDIC tables disagree, D1, #4035) and BI (unsigned, byte order; a step comparing both CH and BI is refused) and ZD and PD (signed, by value); FIELDS=COPY.
  - EQUALS (OPTION or SORT / MERGE operand) is WITH DUPLICATES IN ORDER. Without it (the shipped default, EQUALS=NO)
    the order of equal keys is undefined: two such records with different bytes stop the run by name. A MERGE
    without EQUALS is refused (COBOL's MERGE fixes an order DFSORT does not promise), as is a MERGE on a ZD / PD key.
  - INCLUDE / OMIT COND: a field against a field of the same format and length (or two ZD / PD fields), a C'..'
    constant (cut or blank-padded to the field), X'..' (cut or X'00'-padded) or a decimal against ZD / PD; AND / OR
    with parentheses, AND binding tighter. Applied to each input record before the sort.
  - SORTIN as a concatenation of datasets reads them in order (SORT USING F1 F2).
  - **CH collation case (#4035, #4268).** `carddemo-sort-combtran` (COMBTRAN STEP05R, SORTIN = two datasets, key TRAN-ID 1,16,CH)
    carries TRAN-IDs of letters A-F and digits, so IBM's EBCDIC order (a letter before a digit) differs from the oracle's byte order
    (a digit first): executed-equivalent, SORTOUT 50/50 records equal, RETURN-CODE 0, 1/1 paragraphs. The letters are synthetic

  - **Declared difference.** The oracle's SORT rewrites a signed DISPLAY key's sign zone in the records it sorts
    (`cobc -std=ibm -fsign=EBCDIC`, cobc 3.1.2, measured 2026-10-28: an unsigned key `0001` comes out `000A`); DFSORT
    and Enterprise COBOL never change a record's bytes. The lowering therefore sorts a ZD / PD key as a copy carried
    ahead of the record and writes only the record. The same oracle behaviour applies to a COBOL program's own SORT
    on a signed DISPLAY key over unsigned data; the port keeps the bytes, as IBM does.
  - OUTREC FIELDS= (or BUILD=) rebuilds the output record, after the sort / merge and after INCLUDE / OMIT, from input
    fields (p,m or a SYMNAMES field, CH or BI), nX blanks, nZ binary zeros and C'..' / X'..' constants, each optionally
    after an `o:` position that must be the next free byte. Proven on the SORT, COPY and MERGE writers and on a carried
    ZD key (`OUTREC*` cases of `test_dfsort_4268.py`). Not modelled and refused: a position that leaves a gap or
    overlaps, a decimal or empty constant, a format conversion (ZD, PD ... or edit masks), OVERLAY / PARSE.

- The COBOL SORT / MERGE / RELEASE / RETURN verbs and the SD entry are translated (#4286), onto `cobolrt/Sort`:
  - Keys compare as a relation condition compares their items: a numeric key (zoned, packed, binary, signed or
    not) by value, any other byte by byte. WITH DUPLICATES IN ORDER is a stable sort; without it, records with
    equal keys and different bytes stop the run by name (IBM: their order is undefined). A MERGE input out of key
    order stops the run by name.
  - USING / GIVING files are opened, read or written and closed implicitly; their FILE STATUS items are left as
    they were (GnuCOBOL does not set them; IBM's depends on FASTSRT).
  - COLLATING SEQUENCE (or PROGRAM COLLATING SEQUENCE): NATIVE, STANDARD-1 and STANDARD-2 are the data's byte order
    (D1). EBCDIC and literal alphabets (#4268) order the alphanumeric keys; see D1 for where IBM and GnuCOBOL
    differ.
  - SORT-RETURN (the S9(4) BINARY special register) is read and written like any item. IBM: moving 16 to it in a
    procedure ends the sort at the next RELEASE / RETURN, and a successful sort leaves it 0. GnuCOBOL (measured: a
    16 set in an input procedure and in an output procedure, three sorts) ignores the 16, runs the sort to its end and
    leaves the program's value (a later good sort does not reset it). The two disagree, so the run stops by name
    (`Sort.endsSort`, `Sort.finished`) at a RELEASE / RETURN reached with the register at 16, and at the end of a
    sort with the register not 0. A register set and restored to 0 inside the procedures, or only read, runs
    as both do (SORTRC, three modes against GnuCOBOL). The oracle cannot show IBM's early end; it is not modelled.
  - SORT of a table (format 2: `SORT table ON ASCENDING | DESCENDING KEY k ... [WITH DUPLICATES]`) puts each entry of
    a one-level, fixed-count OCCURS item through the same `Sort` and writes the ordered entries back; the keys are
    items of one entry (or the entry itself, for an elementary table). Proved against GnuCOBOL in `SORTTB` (#4268).
    A table with OCCURS ... DEPENDING ON sorts its first `count` entries (the count read when the SORT runs; the
    entries past it are untouched; a count outside the OCCURS bounds, undefined in IBM, stops the port by name), and a
    SORT with no KEY phrase uses the OCCURS clause's own single KEY (IBM): proved in `SORTDP` (#4268).
  - An SD with records of different lengths (several 01s): RELEASE of any of them, the keys within the shortest
    record, RETURN INTO moving the record's own length (IBM: the receiver is space-padded). Where IBM leaves the
    bytes past a shorter record's end undefined, the port follows cobc (the whole area travels with each record). Proved
    in `SORTVL` (#4268).
  - A fixed USING / GIVING file whose record is shorter than the SD's longest (IBM: a file's record lies between the SD's
    shortest and longest): its records go in at the file's own length and a GIVING file of the same length receives
    them (the oracle writes the first bytes of the area; measured, cobc 3.1.2). Proved in `SORTSH`, with SORT USING /
    GIVING, USING / OUTPUT PROCEDURE and MERGE (#4268). A run whose sorted records are not all the GIVING file's length
    (USING files of two lengths) stops by name.
  - SORT / MERGE USING of RECORD VARYING files (`RECORD IS VARYING IN SIZE FROM m TO n DEPENDING ON item`, with `n` the
    record's size and `m` no shorter than the SD's shortest record): each record is read at its own length, the rest of
    the record area is spaces and the sort carries the area (the oracle's behaviour, measured cobc 3.1.2; IBM sorts the
    record at its own length and leaves the bytes past it undefined, so RETURN INTO, which space-pads, agrees and a
    RETURN read of the bytes past the length is the declared difference). The DEPENDING ON item holds the length of
    the last record read, as the oracle's implicit READ leaves it (IBM does not say; the port follows cobc). Proved in
    `SORTVR` (SORT and MERGE, USING / OUTPUT PROCEDURE, three modes, #4268). **GIVING a RECORD VARYING file is refused,
    and so is any GIVING after a RECORD VARYING USING file:** the oracle writes an EMPTY file for a varying GIVING file
    (measured: four records in, zero bytes out, SORT-RETURN 0) and pads a fixed GIVING file to its length, while IBM
    writes each record at its own length: nothing the oracle can prove. A READ statement of a variable-length file is
    still refused.
  - Refused by name: a format 2 table that is a nested OCCURS, a subscripted key, no KEY phrase over an OCCURS clause
    with no KEY, or with two or more (IBM orders by every OCCURS key, GnuCOBOL by the first only), a key under OCCURS in an SD record, a key past the end of the SD's shortest
    record, a GIVING file whose length differs from a sorted record's (IBM writes each at its own length, GnuCOBOL the file's
    fixed record), a USING / GIVING file whose records fall outside the SD's shortest..longest, a RECORD VARYING USING file that is not FROM m TO n filling its record inside that range, a RECORD VARYING GIVING file,
    an alphabet ordinal (a numeric literal names a native code: EBCDIC on z/OS), HIGH-VALUE / LOW-VALUE in an
    alphabet, and a group key holding numeric items under an alphabet.
