- `gitgalaxy/tools/cobol_to_java/det/idcams_model.py` (`run(sysin, catalog, dds)`, tests `test_idcams_model_8880.py`) runs a
  step's commands against a catalog of clusters, alternate indexes and paths and the step's sequential DDs and returns the step's return code (MAXCC at
  its end). It is the oracle for an IDCAMS step in a job case; `det/idcams.py` (one REPRO lowered onto COBOL, F4) is
  unchanged. **Java runtime (#8881):** `cobolrt/job/Idcams.java` is a second implementation of the model (it is not shipped in
  generated ports: `program.runtime_files` skips `job/`), and `test_idcams_java_8881.py` runs authored decks through both and compares
  return codes, log, catalog, datasets, path records and refusal text. **Not wired yet (#8880 item 3):** the job harness does not run an
  IDCAMS step, so no job case compares one. Evidence level: modelled, unit-tested on authored decks and the Java checked against the model on them; one behaviour is executed-equivalent
  (next bullet), the rest is not.
- **Path order against GnuCOBOL (#8881, `test_idcams_aix_oracle_8881.py`).** A KSDS base's path order (alternate key, then
  the base's primary-key order for equal keys) equals what GnuCOBOL's Berkeley DB alternate key returns through START and
  READ NEXT: 6 inputs (distinct keys, duplicates interleaved across primary keys, one record, all keys equal, descending,
  digits and blanks) x 4 key layouts (primary / alternate key offsets 0/4, 4/0, 0/6, 2/6), 24 runs, 0 differences
  (`gitgalaxy-gnucobol:3`, `EQUIVALENCE_E2E=1`). GnuCOBOL answers 02 on a WRITE whose alternate key repeats, as on the READ.
  **Not covered:** an ESDS base (GnuCOBOL has no ESDS alternate keys, so the arrival-order rule stays an IBM-text
  assumption), UNIQUEKEY over duplicates (refused, never executed), BLDINDEX's condition code and the alternate record
  layout (model only). The oracle is GnuCOBOL, not z/OS.
- **IBM.** z/OS DFSMS Access Method Services Commands (SC23-6846-60), read by section from memory of the text, not re-read
  against the box copy (ibm-manuals idai200): "REPRO", "DELETE", "DEFINE CLUSTER", "DEFINE ALTERNATEINDEX", "DEFINE PATH", "BLDINDEX", "SET", "IF-THEN-ELSE command sequence",
  "Condition codes", "Modal commands", "Continuing commands and comments".
  - Condition codes: LASTCC is the last command's code, MAXCC the highest so far, the step returns MAXCC; `SET MAXCC = n`
    replaces it; a failing command does not stop the next. DELETE of an entry not in the catalog is 8 (entry not found);
    DEFINE of a name already cataloged is 12 (duplicate data set name) and changes nothing. **ASSUMED:** those two codes,
    and that a command after a code-8 or code-12 command still runs (the DELETE-then-DEFINE idiom).
  - REPRO copies fixed-length records; a KSDS reads in key order and is loaded into an EMPTY KSDS in ascending key order;
    an ESDS reads in arrival order and is appended to; a sequential output is rewritten from its start.
  - DEFINE CLUSTER: INDEXED (default) is a KSDS with `KEYS(length offset)`, NONINDEXED an ESDS, `RECORDSIZE(avg max)`.
    **ASSUMED:** allocation (VOLUMES, CYLINDERS, TRACKS, RECORDS, MEGABYTES, KILOBYTES, SHAREOPTIONS, FREESPACE, SPEED,
    RECOVERY, UNIQUE, SUBALLOCATION) always succeeds and changes no byte the model reads; DELETE has no retention
    period, so PURGE / NOPURGE are the same.
  - DEFINE ALTERNATEINDEX (alias AIX) RELATE(base) KEYS(length offset) RECORDSIZE(avg max), UNIQUEKEY / NONUNIQUEKEY
    (default NONUNIQUEKEY), UPGRADE; DEFINE PATH NAME PATHENTRY(aix) (UPDATE / NOUPDATE); BLDINDEX INDATASET(base)
    OUTDATASET(aix) (IDS / ODS). Reading a path (REPRO INDATASET(path), or a DD naming it) yields the base's records in
    alternate-key order; records with one key come out in the order the base holds them (key order for a KSDS, arrival order
    for an ESDS). **ASSUMED (not stated in the text read):** BLDINDEX ends with code 0; an alternate index record is
    5 + alternate key + n x pointer bytes, the pointer being the base primary key length (KSDS) or 4 (ESDS RBA), and the
    busiest key's record must fit RECORDSIZE maximum; a duplicate AIX or path name is code 12 (as for a cluster); the
    abbreviations UNQK, NUNQK, UPG, NUPG, UPD, NUPD.
- **Refused by name** (`Refused`, never a silent success): every other command (ALTER, LISTCAT, PRINT, VERIFY, EXPORT,
  IMPORT, ...), DEFINE of anything but a CLUSTER, ALTERNATEINDEX or PATH, a DATA / INDEX component with more than NAME, CATALOG, NUMBERED / LINEAR / REUSE /
  SPANNED, INDEXED without KEYS, no RECORDSIZE, a key outside the shortest record, DELETE of an entry list or with GDG /
  NONVSAM / other parameters, a password or quoted string, `SET LASTCC`, a SET value over 16, REPRO FROMKEY / TOKEY / SKIP /
  COUNT / REPLACE / REUSE, REPRO of variable-length records, of zero records (its code is not stated), into a non-empty
  KSDS (insert mode), from a source out of key order or with a duplicate key, between two record lengths, onto itself, a DD
  that is not a dataset of the step or whose cluster was deleted in the step, DISP=MOD on an output. For the alternate
  index: NOUPGRADE, RELATE or PATHENTRY not in the catalog (its code is not stated) or of the wrong kind, a PATHENTRY over a
  cluster or another path, a key outside the base's shortest record, BLDINDEX by INFILE / OUTFILE, of an empty base, of an
  already built alternate index, of a UNIQUEKEY alternate index over duplicate keys, with a record over RECORDSIZE, a path
  or alternate index as REPRO output, a read of a path before BLDINDEX, REPRO into a base that has an alternate index (upgrade
  is not modelled), DELETE of an alternate index, a path, or a cluster that has an alternate index.
- Residual risk: the oracle is this model, not z/OS; the two condition codes and the empty-input and out-of-order cases
  above are what a real IDCAMS run on z/OS would confirm or refute.
