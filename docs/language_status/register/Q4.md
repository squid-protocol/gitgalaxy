title: "Unsupported embedded SQL — REFUSED"

---
- **Modelled (#4269).** `WHENEVER {SQLERROR | NOT FOUND | SQLWARNING} {CONTINUE | GO TO label}`: scoped by source
  order, tested against the SQLCA after each executable statement (SQLERROR, then NOT FOUND, then SQLWARNING, as IBM).
  `WHENEVER ... PERFORM` / `STOP` and a label that is not a paragraph are refused by name. A scroll cursor's
  `DECLARE` and its plain `FETCH` (GenApp LGIPDB01) run; no burned estate uses the forms below.
- **Modelled (#4269).** `EXECUTE IMMEDIATE 'INSERT ... VALUES ...'`: the string literal (an embedded quote doubled) is
  the statement text, run as written on the unit of work's connection, Db2 answering (-803, -204, ... land in the
  SQLCA; WHENEVER tests them). Proven on Db2 by the synthetic estate `tests/equivalence/db2/dynsql` (DYNDEMO; no
  burned estate issues dynamic SQL). **Assumption:** the connection returns no row count, so SQLERRD(3) is not set
  by the port while Db2 sets it to 1: a program that reads it after such a statement shows as a differing scenario,
  never as a silent pass. Refused by name: a host variable as the text, a parameter marker, a searched UPDATE / DELETE /
  MERGE and an INSERT ... SELECT (+100 when no row changes, which needs the count), DDL, COMMIT / ROLLBACK, a SELECT,
  and EXECUTE IMMEDIATE in a CICS program.
- **Modelled (#4269).** `PREPARE name FROM 'INSERT ... VALUES ...'` then `EXECUTE name` (no `USING`): the literal is kept
  at the PREPARE and run at each EXECUTE exactly as EXECUTE IMMEDIATE runs it. The PREPARE itself leaves SQLCODE 0
  and touches no row (the port and the oracle both run `VALUES 1`). Proven on the DYNDEMO estate (insert, then
  -803 on the second EXECUTE). **Assumptions:** Db2's -104 for text it cannot parse lands at the EXECUTE, not the
  PREPARE; an EXECUTE reached at run time before its PREPARE (-518) is not modelled (one placed before every PREPARE of
  the name in the source is refused). Refused by name: a name PREPAREd from two different literals, a host variable as
  the text, `INTO` / `ATTRIBUTES`, any text but INSERT ... VALUES, and a CICS program.
- **Modelled (#4269).** `EXECUTE name USING :H [:IND], ...` binding the parameter markers (`?`) of such a PREPAREd
  INSERT ... VALUES, one scalar host variable per marker (an indicator below zero is NULL). Proven on Db2 by DYNDEMO (the
  insert, a quote inside a bound value, -803 on a repeat, -407 for a NULL into a NOT NULL column). **Assumption:** the
  port writes each value into the text as a literal (character quoted with `'` doubled, number as its digits, NULL)
  where Db2 binds it, which gives the same row for an INSERT ... VALUES; a program that reads SQLERRD(3) shows as a
  differing scenario (as above). Refused by name: a marker in EXECUTE IMMEDIATE, a marker count that is not the host
  variable count (Db2 -313), `USING DESCRIPTOR`, a host structure or array, and a CICS program.
- **Modelled (#4269).** `FETCH [INSENSITIVE] {NEXT | PRIOR | FIRST | LAST | CURRENT | ABSOLUTE n | RELATIVE n}` of a
  `DECLARE ... [INSENSITIVE] SCROLL CURSOR`: the rows are read at OPEN and the port keeps a position (0 before the first
  row, 1..n on a row, n+1 after the last; a move off either end clamps there and answers +100 / 02000 with the host
  variables untouched; `ABSOLUTE` of a negative n counts from the end, `ABSOLUTE 0` is before the first row). `n` is a
  literal or an integer host variable. Proven on Db2 (CLI `SQLFetchScroll`) by `tests/equivalence/db2/scrolldemo`
  (SCRDEMO: 20 fetches, a closed cursor -501, an empty cursor). **Assumption:** the rows are fixed at OPEN, so a
  program that updates the table while a cursor is open is not modelled by an INSENSITIVE cursor (it is insensitive).
  The oracle does not log scroll FETCH outcomes (the two sides' fetch counts differ by design); the rows the program sees
  are compared through its output.
- **Modelled, proven on Db2 (#4269).** `FETCH [INSENSITIVE] BEFORE | AFTER [FROM] cursor` of a
  `DECLARE ... [INSENSITIVE | ASENSITIVE] SCROLL CURSOR`: a position and no row. The port parks the cursor before the
  first row (position 0) or after the last (n+1), SQLCODE 0, no host variable touched (`DetSql.positionScroll`, no
  generated repository method: nothing is read); the next `NEXT` / `PRIOR` / `FIRST` ... moves as from any end position,
  and `FETCH CURRENT` there is refused as before. A closed cursor is -501. Checked by a JDK trace over the rows 10..50
  and an empty cursor (`test_detsql_moves_a_position_over_the_rows_read_at_open_as_db2_does`), written from the Db2 for
  z/OS SQL Reference (FETCH). **Proven on Db2** by `tests/equivalence/db2/scrolldemo` (SCRDEMO: AFTER and BEFORE
  then NEXT / PRIOR from each end, the `FROM` and `INSENSITIVE` spellings, an empty cursor): `ggsql.c` runs BEFORE as CLI
  `SQLFetchScroll(ABSOLUTE 0)` and AFTER as `LAST` then `NEXT`, SQLCODE 0, host variable untouched; `equivalence_sql.py`
  takes the no-INTO form for a SCROLL cursor only. No burned estate uses it (pinned by
  `test_no_burned_estate_program_uses_a_positioning_fetch_or_multi_row_sql`).
- **Modelled (#4269).** `FETCH [NEXT] ROWSET [FROM] cursor FOR n ROWS INTO :A1 [:I1], :A2 ...` of a cursor declared
  `WITH ROWSET POSITIONING`: each host variable is an elementary `PIC` table (`OCCURS`), one per column, optionally with an
  indicator table of the same size; row j lands in element j of every table. `n` is a literal or a numeric host variable and
  may not exceed the smallest table. SQLERRD(3) is the number of rows read; a rowset that reaches the end of the data holds
  fewer than `n` rows (or none) and answers +100 / 02000, a full one 0. Proven on Db2 (CLI, one `SQLFetch` a row) by an
  estate built inline in `test_rowdemo_det_port_proves_on_db2_against_the_hand_trace` (literal and host-variable counts,
  a NULL column, a full, a short and an empty rowset, a closed cursor -501). **Assumptions:** the +100 on a short rowset
  and the SQLERRD(3) count are as the Db2 for z/OS SQL Reference states them; the host-variable tables are filled only up to
  SQLERRD(3), the elements past it keep their value; the oracle logs one FETCH a row (the port's JDBC reads row by row), so
  per-query row counts compare unchanged. No burned estate uses it.
- **Modelled (#4269).** `INSERT INTO t (cols) VALUES (:A1 [:I1], :A2 ...) FOR n ROWS [ATOMIC]`: each host variable is an
  elementary `PIC` table (`OCCURS`), one per column, optionally with an indicator table of the same size; row j is built
  from element j of every table. `n` is a literal or a numeric host variable and may not exceed the smallest table. The
  port runs the single-row INSERT once a row (`DetSql.insertRows`); SQLERRD(3) is the number of rows inserted. A failure on
  the first row gives that row's SQLCODE and SQLERRD(3) 0 (proven: duplicate key -803). Proven on Db2 by an estate built
  inline in `test_insdemo_det_port_proves_on_db2_against_the_hand_trace` (literal and host-variable counts, a NULL through
  an indicator, a first-row duplicate key, the row count read back). **Assumptions:** ATOMIC is the default and undoes the
  statement on a failure; the port models it with an internal savepoint (`GGINSROWS_UNDO`) on the unit of work, so a
  mid-rowset failure leaves no rows and SQLERRD(3) 0 (proven on Db2: duplicate on row 2 and on the last row). Without a
  unit of work a failure after the first row is still refused. NOT ATOMIC CONTINUE ON SQLEXCEPTION stays refused. No burned estate uses it.
- **Modelled, proven on Db2 (#4269).** `COMMIT [WORK]` and `ROLLBACK [WORK]` end the unit of work a batch (DSN / CAF) step
  runs in (`DetSql.commit` / `rollback`). COMMIT makes the work since the last COMMIT durable and closes the cursors not
  declared `WITH HOLD`; ROLLBACK undoes the work since the last COMMIT and closes every cursor, so a FETCH after it is -501.
  `SAVEPOINT`, `ROLLBACK TO SAVEPOINT` and `RELEASE SAVEPOINT` run as written on the same connection (a released savepoint
  answers -880). A step that abends is backed out to its last COMMIT, and the table is compared after the abend. **Proven
  on Db2** by `tests/equivalence/db2/uow` (UOWDEMO, modes N and A: `test_uowdemo_det_port_proves_on_db2_against_the_hand_trace`,
  under `EQUIVALENCE_E2E`): output against a hand trace, and the rows read back from Db2 equal on both sides. **Assumption:**
  the oracle is GnuCOBOL plus our stub, not z/OS. In a CICS program COMMIT is the task's (a no-op reset) and `ROLLBACK`
  (Db2 for z/OS answers -926, SQLSTATE 2D521; `SYNCPOINT ROLLBACK` backs out) and `ROLLBACK TO SAVEPOINT` are refused by
  name; `COMMIT` / `ROLLBACK` with another option, or inside EXECUTE IMMEDIATE, are refused.
- **Refused (#4269), by form; burned estates using any of them: none** (pinned live by `test_no_burned_estate_program_issues_a_refused_dynamic_or_connection_sql_verb`
  in `tests/cobol_mainframe/test_sql_dynamic.py`, which fails when a burned program starts to use one; first run 2026-10-23).
  Each stops the det translator with `EXEC SQL <verb>: <form> (register Q4 ...)`:
  - `DESCRIBE` (SQLDA of a prepared statement or table): needs an SQLDA model; modelled when a burned program describes.
  - `CONNECT [TO loc | RESET]`: the port has one connection per run; a location switch needs a second oracle database.
  - `EXEC SQL CALL proc (...)`: a stored procedure needs a procedure fixture on the oracle (and result-set rules).
  - `PREPARE` of other text or from a host variable, `EXECUTE ... USING DESCRIPTOR`, `ALLOCATE` / `ASSOCIATE`: as above.
    The premise pin covers every verb of `_REFUSED_VERBS` (`test_the_burned_estate_pin_covers_every_refused_verb`).
  - A `SET` that does not assign a host variable (`SET CURRENT SQLID`, ...).
  - Scroll `FETCH` of a `SENSITIVE` / `DYNAMIC` cursor (even a plain `NEXT`: the rows are read once at OPEN), `FETCH BEFORE` /
    `AFTER` with an `INTO` or on such a cursor, an orientation on a cursor not declared `SCROLL`, and `SCROLL` with `WITH HOLD` (the oracle's held-cursor
    position across COMMIT is unmeasured). `FETCH CURRENT` with no current row is refused at run time (Db2 for z/OS
    answers +231, Db2 LUW +100).
  - Multi-row `FETCH ... ROWSET` with `STARTING AT`, an orientation (`PRIOR` / `FIRST` / ... `ROWSET`) or no `FOR n ROWS`,
    `INSERT ... FOR n ROWS NOT ATOMIC CONTINUE ON SQLEXCEPTION` (or a `FOR n ROWS` not at the end), and a host-variable
    array used anywhere but as a ROWSET FETCH or INSERT ... FOR n ROWS column: each stops the det
    translator by name (`a multi-row FETCH / INSERT ... (register Q4)`, `host variable array X`).
    Pinned by `test_no_burned_estate_program_uses_a_scroll_fetch_or_multi_row_sql`
    (`tests/cobol_mainframe/test_sql_dynamic.py`): it fails when a burned program starts to use one.
  - A host variable in a savepoint statement (Q3) stops the precompiler and the det translator by name (and a
    savepoint statement in a CICS program the det translator), as does an undeclared host variable or a
    `WHERE CURRENT OF` a cursor the program does not declare. A positioned UPDATE / DELETE on a declared cursor runs (Q8).
