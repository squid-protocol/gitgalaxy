- **IBM.** A put with MsgId MQMI_NONE gets a unique MsgId from the queue manager, returned in the MQMD; its form is
  the queue manager's own. An object handle is an opaque value.
- **Assumed.** Both models make the MsgId `GGMQ` followed by a 20-digit counter (and a stated message with no MsgId
  `GGMQSTATED` and its number), and the handles 1, 2, 3 ... in the order opened; MQCLOSE sets the handle to
  MQHO_UNUSABLE_HOBJ (-1), as IBM documents. A program that depends on the form of either (rather than its identity)
  would differ from z/OS; no modelled program does.
- **Not modelled.** MQPMO_NEW_MSG_ID / NEW_CORREL_ID (refused by name), MsgId / CorrelId matching on MQGET (a get
  whose MQMD carries an id other than MQMI_NONE / MQCI_NONE is refused), message groups and segments.

- **IBM (document).** IBM MQ Application Programming Reference, the MQMD structure (MsgId: the queue manager
  generates a unique id when MQMI_NONE is given) and MQCLOSE (the handle is set to MQHO_UNUSABLE_HOBJ)
  (https://www.ibm.com/docs/en/ibm-mq/9.3?topic=reference-mqmd-message-descriptor). The wording is paraphrased, not
  verbatim.
- **Declared difference.** The `GGMQ` + 20-digit MsgId form and the handle numbers 1, 2, 3 are the models', not
  z/OS's. IBM does not define the form, so the comparator expects the two models to agree with each other only.
- **IBM trace (#8700, 2026-11-20; IBM MQ 9.4 Developing Applications Reference, MQMD "MsgId", MQPMO "Context options",
  MQOPEN "Hobj", MQCLOSE "Hobj"; the register cites 9.3).** Rules `RT-MQ-OPEN`, `RT-MQ-CLOSE`, `RT-MQ-PUT`.
  - **DIFFERS, the MsgId form (RT-MQ-PUT).** The "IBM" bullet above says the form is the queue manager's own. The 9.4 text is
    more specific: "A MsgId generated by the queue manager consists of a 4-byte product identifier (AMQ¬ or CSQ¬ in
    either ASCII or EBCDIC, where ¬ represents a blank character), followed by a product-specific implementation of a
    unique string. In IBM MQ this contains the first 12 characters of the queue manager name, and a value derived from
    the system clock." The runtime's `GGMQ` + 20-digit counter has neither the CSQ prefix nor the queue manager name:
    the declared difference below, now with IBM's form quoted. Uniqueness ("the queue manager generates a unique message
    identifier") holds.
  - **Put context matches Table 529.** MQPMO_DEFAULT_CONTEXT: UserIdentifier "Determined from the environment if possible;
    set to blanks otherwise", AccountingToken "set to MQACT_NONE otherwise", PutApplType "Determined from the
    environment", PutDate / PutTime "Set to the date when message is put", ApplIdentityData / ApplOriginData blanks;
    "These are the default values and actions if no context options are specified." MQPMO_NO_CONTEXT: "Blanks for
    character fields, Nulls for byte fields, Zeros for numeric fields". PutDate / PutTime: "Greenwich Mean Time (GMT)
    is used ... subject to the system clock being set accurately to GMT". PutApplType MQAT_CICS is value 1 (constants).
    The placeholders are IBM's "otherwise" values; the real values need a task, which the case lacks.
  - **Still ASSUMED, the handle (RT-MQ-OPEN).** MQOPEN Hobj: "It must be specified on subsequent IBM MQ calls ... It ceases
    to be valid when the MQCLOSE call is issued"; no value is defined, so 1, 2, 3 is the oracle's choice.
  - **Still ASSUMED, MQCLOSE (RT-MQ-CLOSE), and a correction to the "as IBM documents" claim above.** MQCLOSE Hobj: "On
    successful completion of the call, the queue manager sets this parameter to ... MQHO_UNUSABLE_HOBJ", then "On z/OS,
    Hobj is set to a value that is undefined." The runtime sets -1 (MQHO_UNUSABLE_HOBJ, X'FFFFFFFF'); on z/OS IBM does not
    say it does. A program reading Hobj after MQCLOSE relies on the oracle's choice; none is modelled.
