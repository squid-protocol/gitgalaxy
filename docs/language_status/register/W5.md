- **IBM.** Under CICS the MQ unit of work is the task's: EXEC CICS SYNCPOINT commits it, SYNCPOINT ROLLBACK and an
  abend that ends the task back it out, and the task's normal end commits it. On z/OS a get or put with neither
  SYNCPOINT option is within the unit of work. A message put in a unit of work is not available until it commits; one
  got in it is restored by a backout with its MQMD BackoutCount raised by one.
- **Modelled.** ggcics.c's `uow_end` (SYNCPOINT, ROLLBACK, abend backout) tells ggmq.c (`ggmq_uow_end`, a weak hook as
  ggsql's); CicsTask tells its joined resource managers at the same three points (`withResource`, #4892); both
  models commit at the task's normal end before the queues it leaves are compared (the `MQ-QUEUES` event).
- **Assumed.** That the task's normal end is a commit for every program, as CICS documents for a task ending with
  RETURN; a SYNCPOINT ROLLBACK after a SYNCPOINT stays refused by CicsTask as before.
- **Not modelled (refused).** MQCMIT, MQBACK, MQBEGIN (an MQ unit of work of its own; no burned source names one, pinned by
  `test_no_burned_program_names_an_mq_unit_of_work_call`, #5259, so there is nothing burned to prove), MQGMO_SYNCPOINT_IF_PERSISTENT,
  MQGMO_MARK_SKIP_BACKOUT, backout thresholds and requeueing.

- **IBM (document).** IBM MQ Application Programming Guide, using MQ in a CICS program (the MQ unit of work is the
  CICS task's; SYNCPOINT commits, SYNCPOINT ROLLBACK backs out), and the IBM MQ Application Programming Reference,
  MQGMO (MQGMO_SYNCPOINT, MQGMO_NO_SYNCPOINT) and the MQMD BackoutCount field
  (https://www.ibm.com/docs/en/ibm-mq/9.3?topic=reference-mqgmo-get-message-options). The wording is paraphrased, not
  verbatim.
- **Declared difference.** None for the modelled points. The one assumption (the task's normal end commits for every
  program) is stated above; the refused calls are not a difference, they are not run.
- **IBM trace (#8700, 2026-11-20; IBM MQ 9.4 Developing Applications, "Syncpoints in CICS Transaction Server for z/OS
  applications"; Developing Applications Reference, MQGMO "MQGMO_SYNCPOINT" and MQMD "BackoutCount"; the register cites 9.3).**
  Rule `RT-MQ-UNIT-OF-WORK`.
  - **Matched:** "In a CICS application you establish a syncpoint by using the EXEC CICS SYNCPOINT command. To back out all
    changes to the previous syncpoint, you can use the EXEC CICS SYNCPOINT ROLLBACK command." "If the application closes
    down normally, any open queues are closed and an implicit commit occurs. If the application closes down abnormally,
    any open queues are closed and an implicit backout occurs." (so the normal-end commit above is IBM's, for any
    program, not an assumption). With neither syncpoint option "On z/OS, the get request is within a unit of work";
    a get under syncpoint "is deleted from the queue only when the unit of work is committed. The message is made
    available again if the unit of work is backed out". BackoutCount: "the number of times that the message has been
    previously returned by the MQGET call as part of a unit of work, and subsequently backed out".
  - **Undeclared difference (found by this trace):** BackoutCount "On z/OS, a value of 255 means that the message has been
    backed out 255 or more times; the value returned is never greater than 255". `QueueManager.uowEnd` adds one with no
    cap. Not reached: a case would need 255 rollbacks of one message. The rule stays ASSUMED until the cap is applied or
    declared.
  - **Also IBM:** "If a CICS application issues the MQDISC call, no implicit syncpoint is taken." The joint syncpoint with
    `ggcics.c` stays the oracle's.
