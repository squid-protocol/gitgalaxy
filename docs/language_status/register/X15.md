- **What IBM documents** (CICS TS, EXEC CICS RECEIVE (3270 logical), ibm.com/docs/en/cics-ts/6.x?topic=summary-receive-3270-logical,
  and (LUTYPE2/LUTYPE3); wording paraphrased): with INTO and no
  MAXLENGTH, LENGTH is "the maximum length that the program accepts" (below zero, zero); MAXLENGTH overrides it;
  longer data is truncated with LENGERR and LENGTH "set to the original length of data", or, under NOTRUNCATE, "CICS
  retains the remaining data and uses it to satisfy subsequent RECEIVE commands" with LENGTH the length returned.
  On an LUTYPE2 terminal EOC "occurs when a request/response unit (RU) is received with end-of-chain-indicator set",
  default action: ignore it (the 3270 logical unit's RECEIVE has no EOC). HANDLE CONDITION ERROR takes only a
  condition whose default action is an abend, so not EOC. SEND CONTROL sends device controls; none of its
  conditions can arise without a BMS logical message, partitions, LDCs or REQID. Both sides model it: `ggcics.c`
  GGCRECT / GGCRECS / GGCSCTL, and CicsTask.receive / sendControl with `DetCics.received` / `receivedSet`.
- **Assumed.** The terminal is the reference region's 3270 logical unit unless the case CSD defines it with a
  TYPETERM `DEVICE(LUTYPE2)` (cics-crucible SPEC section 2): then the input message is one chain, its single RU
  carries end-of-chain, and the RECEIVE returning its last byte raises EOC. RECEIVE INTO moves the data into INTO's
  first bytes and leaves the rest as it was. RECEIVE SET(ADDRESS OF record): the port's LINKAGE record keeps its own
  storage, so the data is copied into it and the bytes past the data are X'00' (on CICS they are storage IBM does not
  describe; a program reading past LENGTH reads undefined bytes).
- **Equivalence harness (#7434).** A case or scenario states the device as `"device": "LUTYPE2"` (or `"3270"`, the default;
  anything else is refused): the stub gets `GGCICS_LU2=1`, the port `CicsTask.withEndOfChain(true)`. A RECEIVE that raises
  EOC still delivers its data, so the comparator reads the stub's data for RESP EOC as for NORMAL and LENGERR. Reached by
  equivalence cases cruc-hc-terminal-eoc (HCEOC) and cruc-hc-eoc-error (HCEOE).
- **SET without MAXLENGTH (#5079, ruling).** With SET, IBM makes LENGTH an output ("the data area is set to the length of
  the data"), so the "value indicated in the LENGTH option is assumed" default has no input to read and nothing bounds the
  data: the whole retained input is delivered, LENGTH is its length, never LENGERR, and NOTRUNCATE has nothing to retain.
  The det port passes `Integer.MAX_VALUE` to `CicsTask.receive`; the stub passes its 32768-byte buffer size. Both SET forms
  (ADDRESS OF record, pointer: X58) follow it, which supersedes X58's "MAXLENGTH required" clause. Reached by cics-crucible
  `ca-receive-retrieve-set` (3 scenarios, terminal input shorter than the stub buffer). CARCST and CARTWK have committed det ports (14/14 each, no holes): `short-input` passes
  both Java sides; the other two differ from the crucible's log only at RSLOG item 1 (IBM: 2, as the cobol-stub).
- **Refused by name** (`Unsupported` / CicsError, "... not modelled"): SET of anything but ADDRESS OF a LINKAGE 01
  record; SET without LENGTH(data-area); ASIS, BUFFER and the APPC / partition options; SEND CONTROL CURSOR
  without a value, PRINT, FORMFEED, ALTERNATE / DEFAULT, MSR, partitions, LDC, ACCUM / PAGING / SET / REQID. At run
  time: a RECEIVE with nothing retained (it would wait for the operator), and on an LUTYPE2 terminal a NOTRUNCATE
  RECEIVE that leaves data retained (IBM does not say whether it raises EOC).
- **Reached.** cics-crucible hc-terminal-receive (7 scenarios: LENGERR by RESP, by HANDLE CONDITION and by default,
  NOTRUNCATE pieces, SET, SEND CONTROL with CURSOR) and hc-terminal-eoc (3: EOC by RESP, HANDLE CONDITION, ignored by
  default), cobol-stub and the det port both passing the hand-written logs.
- **IBM trace (#8700, 2026-11-20; CICS TS for z/OS 6, API Reference, Chapter 2 "CICS command summary", RECEIVE (3270 logical)
  and RECEIVE (LUTYPE2/LUTYPE3); the two pages carry the same option and condition text).** Rule `RT-CICS-TERMINAL-RECEIVE`
  stays **ASSUMED**: the quotes below match its LENGTH / MAXLENGTH / NOTRUNCATE / SET length behaviour, and leave open
  what it names as the choice.
  - **MATCHED.** LENGTH: "If you specify the INTO option, but omit the MAXLENGTH option, the argument must be a data area
    that specifies the maximum length that the program accepts. If the value specified is less than zero, zero is assumed."
    MAXLENGTH: "If the length of data exceeds the value specified and the NOTRUNCATE option is not present, the data is
    truncated to that value and the LENGERR condition occurs. The data area specified in the LENGTH option is set to the
    original length of data"; with NOTRUNCATE "CICS retains the remaining data and uses it to satisfy subsequent RECEIVE
    commands. The data area specified in the LENGTH option is set to the length of data returned"; "If this option is
    omitted, the value indicated in the LENGTH option is assumed." LENGERR: "Occurs if data is discarded by CICS because its
    length exceeds the maximum the program accepts and the NOTRUNCATE option is not specified." The SET ruling (#5079)
    is IBM's: "If you specify the SET option, the argument must be a data area. When the data has been received, the data
    area is set to the length of the data." EOC: "Occurs when a request/response unit (RU) is received with
    end-of-chain-indicator set. Field EIBEOC also indicates this condition. Default action: ignore the condition."
  - **Still ASSUMED, INTO's tail and SET's tail.** The page says only that INTO is "the receiving field for the data read";
    it does not say what the bytes of INTO past the data hold (the runtime leaves them as they were), nor what lies past the
    data a SET pointer addresses (the runtime's X'00'). SET: "The pointer reference is valid until the next receive command
    or the end of task" (the port's copy lives for the record's own scope: no program of the cases reads it later).
  - **Still ASSUMED, EOC on a 3270 logical unit.** The 3270 logical page lists EOC among its conditions in the same words as
    LUTYPE2's, so "the 3270 logical unit's RECEIVE has no EOC", stated in the Assumed paragraph above, is not IBM's: the page does not say when a
    3270 logical unit's RU carries end-of-chain. The runtime raises EOC only for the case's stated LUTYPE2 device; the
    default 3270 never does. Open, not a DIFFERS: IBM names no input that raises it on a 3270.
