- **What IBM documents** (CICS TS 6.x, EXEC CICS MOVE CONTAINER (CHANNEL), STARTBROWSE CONTAINER (CHANNEL), GETNEXT CONTAINER
  (CHANNEL), ENDBROWSE CONTAINER (CHANNEL): https://www.ibm.com/docs/en/cics-ts/6.x?topic=summary-move-container-channel and its
  `startbrowse-` / `getnext-` / `endbrowse-container-channel` siblings). MOVE: CONTAINER names the source, AS the target ("If it
  already exists, its contents are overwritten"), CHANNEL the source's channel and TOCHANNEL the target's ("If the channel does not
  exist, CICS creates it"); each omitted means the current channel. CHANNELERR 1 (illegal TOCHANNEL name), 2 (CHANNEL not found),
  3 (read-only channel); CONTAINERERR 10 (source not found), 18 (illegal AS name); INVREQ 4 (CHANNEL or TOCHANNEL omitted, no
  current channel, outside a BTS activity), 30 / 31 (a CICS-defined read-only container as source / target). STARTBROWSE: CHANNEL
  ("must be either the current channel or a channel created by the program"; omitted with no current channel it "is treated as
  STARTBROWSE CONTAINER (BTS)"), BROWSETOKEN a fullword; CHANNELERR 2. "The order of returned containers is undefined and may
  change." GETNEXT: CONTAINER(data-area) "the 16-character name of the next data-container", BROWSETOKEN a fullword; END 2 (no more
  containers), ILLOGIC 1 (a current token, but not a container browse's), TOKENERR 3 (not valid: after the browse ended, after a
  sync point before it completed, or no STARTBROWSE). ENDBROWSE: ILLOGIC 1, TOKENERR 3. The unhandled conditions abend AEIU
  (ILLOGIC), AEXK (END) and AEZL (TOKENERR) (IBM's AEI/AEY/AEZ abend table; APAR PK43600 shows GETNEXT CONTAINER's TOKENERR as AEZL).
  Both sides model it: `ggcics.c` GGCMOVC / GGCSBRC / GGCGNXC / GGCEBRC and CicsTask moveContainer / startBrowseContainer /
  getNextContainer / endBrowseContainer; the spec entries are `standards/cics/commands/containers.py`.
- **Assumed.** (1) The browse returns the containers in the order they were created; IBM calls the order undefined, so a program
  that depends on it is outside what IBM promises, and the port and the stub agree on this one order. A container MOVEd to a new
  AS is created at that moment; an overwritten AS keeps its place. (2) Tokens are 1, 2, 3 ... in the order the task started
  browses (IBM only says "token"); a token is the issuing program's own: another program (a LINKed one) naming it gets TOKENERR 3
  (IBM: "meant only for the program that issued STARTBROWSE"); a SYNCPOINT (and a ROLLBACK) ends every browse. (3) After END, a
  further GETNEXT is END again; the token stays valid until ENDBROWSE. (4) The browse lists the names at STARTBROWSE; a GETNEXT
  after a container was added to or removed from the channel is refused (below), so no program here sees the unspecified middle
  ground; PUT over an existing container and a MOVE onto an existing AS change data, not names, and are allowed. (5) A MOVE that
  raises a condition changes nothing and creates no TOCHANNEL; the conditions are checked in the order INVREQ 4, CHANNELERR 2,
  CONTAINERERR 10 (IBM does not rank them). (6) The moved container keeps its data type (BIT / CHAR); the bytes are never
  converted, as for PUT / GET (X17). (7) GETNEXT's CONTAINER area takes the 16-character name, blank-padded; a shorter program area
  takes its first bytes.
- **Refused by name** (`CicsError` / `Unsupported` at translation, exit 98 / UnsupportedOperationException at run time): any
  option IBM's command does not list; MOVE CONTAINER onto itself (the same name in the same channel: IBM does not say); MOVE onto an
  existing container of the other data type (its type, or an INVREQ, is not documented; the same open question PUT has, X17);
  GETNEXT after the browsed channel gained or lost a container (IBM says nothing of changes during a browse); STARTBROWSE with no
  CHANNEL and no current channel (IBM: the BTS form, not modelled); a channel an XCTL left behind and a blank / embedded-blank name
  (X17's refusals). **Unreachable, so no outcome:** CHANNELERR 1 and CONTAINERERR 18 (the names' illegal-character rules are not
  modelled: such a name is refused, X17), CHANNELERR 3 and INVREQ 30 / 31 (no channel or container is read-only as an outcome: IBM
  lists no CICS-defined read-only container or channel, see the next item), ILLOGIC 1 (no other browse hands out a token: WEB browses and INQUIRE URIMAP's have none).
- **CICS-defined names (#5005, also DELETE CHANNEL, X44).** IBM's MOVE CONTAINER page gives INVREQ RESP2 30 ("You cannot move a
  CICS-defined read-only container"), 31 (a move onto an existing CICS-defined read-only container) and CHANNELERR RESP2 3 ("the
  current channel or the channel specified on CHANNEL is read-only"); DELETE CHANNEL's page gives CHANNELERR 3 for a read-only channel
  (read 2026-10-31, https://www.ibm.com/docs/en/cics-ts/6.x?topic=summary-move-container-channel and `summary-delete-channel`).
  Neither says which containers or channels are CICS-defined or read-only (DFHTRANSACTION is the only DFH name either mentions, and
  DELETE CHANNEL bars it for another reason), and neither reserves a DFH prefix. So MOVE CONTAINER with a container, AS, CHANNEL or
  TOCHANNEL name beginning DFH, and DELETE CHANNEL of a DFH channel, are **refused by name** on both sides, never run as on an
  ordinary one; DELETE CONTAINER with a DFH container or CHANNEL name is refused the same way (its page, read 2026-10-31, gives INVREQ RESP2 30
  "You cannot delete a CICS-defined read-only container" and CHANNELERR 3, and lists no names either; 0 programs in the burned and
  local corpora use DELETE CONTAINER, `cics_census.py usage "DELETE CONTAINER" --no-census`). GET CONTAINER and the browse are
  unchanged (reading a read-only item is legal). PUT CONTAINER's page gives INVREQ 30 / CHANNELERR 3 too: a PUT naming a DFH channel, or a DFH
  container other than `DFHREQUEST`, `DFH-BODY` and `DFH-DATA`, is refused by name; those three are the pipeline containers DBB
  `epscsmrd.cbl` reads and writes back (the only DFH names a burned program PUTs, grepped 2026-10-31), so they run as ordinary ones.
  LINK, XCTL and RETURN with CHANNEL(DFH...) not already in the program's scope are refused by name too (a DFH channel the harness handed the task, e.g. `DFHEP.EVENT` in genapp-lgastat1, is in scope and used as is), for a different reason (read 2026-10-31,
  `summary-link`, `summary-xctl`, `summary-return`): their pages list no read-only condition (CHANNELERR has RESP2 1 only), but
  say CHANNEL(DFHTRANSACTION) selects the transaction channel, "always accessible in the task" when the link level changes. That
  scope is not modelled, and without the refusal a DFHTRANSACTION run as an ordinary channel and dropped out at the next level.
  (`RUN` / `START` CHANNEL already refused DFH names.) GET, GET64, the browse and QUERY CHANNEL are unchanged.
  **Class pin (#5005):** `tests/cics_crucible/test_cics_dfh_class_5005.py` lists every spec command that names a channel or
  container and fails on one with no stated DFH disposition. Refused by name: PUT, PUT64, DELETE CONTAINER, MOVE, DELETE CHANNEL, START,
  RUN, LINK, XCTL, RETURN (PUT64 is the PUT command with 64-bit areas and shares its refusal and runtime call). Reads, unchanged
  (reading a read-only item is legal): GET, GET64, the browse, QUERY CHANNEL, FETCH ANY / CHILD, ASSIGN CHANNEL; WEB's CHANNEL / AS are HTTP options.
  Still not modelled: the real outcomes, which need an IBM list of the read-only names. Census 2026-10-31 (`cics_census.py usage "MOVE CONTAINER" --no-census`): 0 programs
  in the burned and local corpora use MOVE CONTAINER, and no burned program deletes a DFH channel, so no estate needs the real
  outcomes; they need an IBM list of the read-only names. Proved in `tests/cics_crucible/test_cics_runtimes.py`.
  **Searched again 2026-11-01 for that list, none found:** IBM's CICS TS 6.x "Control containers" page (DFHFUNCTION, DFHERROR: web-services
  pipeline containers) and the CICS TS 5.6 "Channels and containers" page describe CICS-supplied containers and the DFHTRANSACTION
  channel, but none states which are read-only, and no page found lists the names MOVE / PUT / DELETE CONTAINER's INVREQ RESP2 30 / 31 or
  CHANNELERR 3 refer to. The item stays blocked on an IBM source, not on code: the by-name refusals above are the disposition until one is found.
  **Burned-estate pin (#5005, 2026-11-01):** `tests/cics_crucible/test_cics_dfh_burned_corpora_5005.py` scans the six burned estates' COBOL for quoted DFH
  names and fails on any beyond `DFHREQUEST`, `DFH-BODY`, `DFH-DATA` (DBB `epscsmrd.cbl`, PUT back, run as ordinary) and the four `DFHEP.*` names
  (GenApp `lgastat1.cbl`, read only). So no burned program meets a real INVREQ 30 / 31 or CHANNELERR 3 outcome; the checklist item is closed for the
  burned estates, and the outcomes for any other estate stay refused until an IBM list exists.
- **BTS browse forms (#5005, 2026-11-01).** STARTBROWSE / GETNEXT / ENDBROWSE ACTIVITY and PROCESS (and the EVENT / TIMER browses) stay refused
  by name (`standards/cics/commands/api.py`, BTS reason, X65): IBM's channel browse is the CONTAINER form, and BTS is out of scope unless an estate
  needs it. `tests/cics_crucible/test_cics_bts_browse_burned_corpora_5005.py` scans the six burned estates' COBOL and fails on any EXEC CICS
  statement for a command refused with the BTS reason; none exists today. The one browse that reads like BTS, DBB `epscsmrd.cbl`'s
  `STARTBROWSE CONTAINER` with no CHANNEL, runs on the task's current channel (the modelled form; only no CHANNEL and no current channel is
  refused). Other estates keep the refusal.
- **Reached.** Unit proofs: `tests/cics_crucible/test_cics_runtimes.py` runs one 31-step scenario (MOVE across, within and to a new
  channel, onto an existing container, every condition; browse to END, ENDBROWSE, a reused token, a never-given token, a sync point,
  another program's token) on the stub and on CicsTask, which print the same lines, and the refusals above on both. cics-crucible `ca-channel-browse` (companion PR on the crucible, branch `cases/5005-channel-browse`, not pinned) is
  the hand-traced case: it names only ordinary channels and containers. **No crucible log holds a DFH-name disposition:** a log is
  IBM's documented outcome, IBM names no CICS-defined read-only item, and the case format has no refusal. The refusals are proved
  by the unit proofs above; `tests/cics_crucible/test_cics_dfh_case_5005.py` fails when a crucible `ca-channel-*` case names a
  quoted DFH literal, which would be refused by name instead of run.
