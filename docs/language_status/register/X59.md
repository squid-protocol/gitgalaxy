- **ADDRESS** (CICS TS 6.x, https://www.ibm.com/docs/en/cics-ts/6.x?topic=summary-address). EIB "returns a pointer reference set to the address
  of the EXEC interface block (EIB)"; COMMAREA "returns a pointer reference, set to the address of the communication area (COMMAREA) available
  to the currently executing program"; "If the COMMAREA does not exist, the pointer reference is set to the null value, X'FF000000'". CWA, TWA,
  TCTUA (of the principal facility) and ACEE return the address of the common work area, transaction work area, terminal control table user
  area and access control environment element; a missing one is set to the same null value. The page lists no condition (RESP / RESP2 /
  NOHANDLE are the common options) and has no COBOL note.
- **What the runtimes do.** The det port lowers EIB to `DetCics.setPointerToRecord(task, ptr, DFHEIBLK)` and COMMAREA to
  `DetCics.addressCommarea(task, ptr, DFHCOMMAREA, EIBCALEN)`; the stub's `GGCADDR` stores the address of the EIB or of the program's
  DFHCOMMAREA in the pointer. The port's pointer holds the handle of the record's own bytes (X47), the stub's a real address, so SET ADDRESS OF
  record TO pointer makes the record and the EIB (or the DFHCOMMAREA) one storage in both. EIBRESP and EIBRESP2 are written NORMAL, and RESP /
  RESP2 as for any command. Several options in one command are taken in the order EIB, COMMAREA.
- **TWA and TCTUA (#5079 slice 2).** The det port lowers them to `DetCics.addressTwa(task, ptr)` / `DetCics.addressTctua(task, ptr)`: the pointer holds
  the handle of the area's own bytes, sized by the definitions (TRANSACTION TWASIZE, the terminal's TYPETERM USERAREALEN; crucible case
  `ca-address-twa-tctua`). The TWA is the root task's, so every LINK level sees the same bytes; the TCTUA belongs to the terminal and outlives the
  task. An area of size 0 or no stated size is IBM's X'FF000000'. IBM does not state the initial content, so a program that reads before it writes
  is outside the proof. Options are taken in the order EIB, COMMAREA, TWA, TCTUA. **The stub models them too** (slice 2b): `GGCADDR`
  returns one zero-filled block per area, sized by `GGCICS_TWASIZE` / `GGCICS_USERAREALEN` (the harness passes the definitions' values). The TWA is
  one block for the process, so a LINKed program sees the same bytes; the TCTUA is kept in a file beside the scenario's temporary-storage
  directory (`GGCICS_TCTUA`), read back at its first use and written at exit, so it outlives the task. No stated size is the pointer `0xFF`, whose
  first four bytes read as X'FF000000' through a `PIC X(4)` view. The three `ca-address-twa-tctua` `cobol-stub` cells pass; no `java` cell does
  (the crucible `java` side is the forge's stub, not a port). No burned estate program issues either command.
- **CWA (#5079 slice 2a).** The det port lowers it to `DetCics.addressCwa(task, ptr)`: the handle of the region's common work area, SIT WRKAREA
  bytes ("the number of bytes ... for the common work area"), the same bytes for every task and LINK level (crucible case data `wrkarea`).
  **Unstated WRKAREA (decision):** a case that states none, or 0, gets IBM's X'FF000000' as for TWA and TCTUA; the port invents no size
  (IBM documents a SIT default, but a default nobody stated would loosen the proof). IBM does not state the initial content, so a program that reads
  before it writes is outside the proof. Options are taken in the order EIB, COMMAREA, CWA, TWA, TCTUA. **The stub models it too** (slice 2b):
  `GGCADDR` returns one zero-filled block of `GGCICS_WRKAREA` bytes (the harness passes the case's `wrkarea`); the CWA is the region's, so its
  bytes are kept in a file beside the scenario's temporary-storage directory (`GGCICS_CWA`), read back at the first use and written at exit, and
  every task sees what the last wrote. No stated size is the pointer `0xFF` (X'FF000000' through a `PIC X(4)` view). The crucible case `commarea-mismatch/ca-address-cwa` (cics-crucible#47, `wrkarea` 32; scenarios
  `cwa-shared`, `cwa-two-tasks`) issues it and its `cobol-stub` cells pass; it is not in the pinned ref until the next tag, and its `java`
  cells fail as the TWA case's do (the forge's stub, not a port). A stated size is crucible-proven; no size, or 0, is this entry's decision only. No burned estate program issues it.
- **Assumed.** (1) The EIB the pointer addresses is the task's own, updated by every later command as the program's DFHEIBLK is. (2) The
  COMMAREA the pointer addresses is the program's DFHCOMMAREA (the area the caller passed, X23), at its start. (3) The command raises no condition
  (the page lists none).
- **Refused by name.** At translation: ACEE (the region defines none: no CICS system tables); in the harness translator, the old ADDRESS SET form,
  ADDRESS COMMAREA in a program with no LINKAGE 01 DFHCOMMAREA (there is no record to address; the pointer could only be handed to SET ADDRESS OF
  another record), ADDRESS with neither EIB nor COMMAREA, a pointer that is not a plain USAGE POINTER item or that a REDEFINES overlays (X47). At
  run time: ADDRESS COMMAREA when EIBCALEN is 0 (IBM's X'FF000000' is not NULL, and a handle is no number the program can compare with it). BLL cells
  (OS/VS COBOL, X56) keep ADDRESS TWA / CWA a hole for the same reason.
- **The old-style sweep (refused whole, by name; each with its own reason in `standards/cics/commands/api.py`).**
  - **SEND PAGE** (https://www.ibm.com/docs/en/cics-ts/6.x?topic=summary-send-page): "completes a BMS logical message" and "causes BMS to
    generate a device-dependent data stream for the last (perhaps the only) page of data"; RETAIN / RELEASE, OPERPURGE; conditions IGREQCD,
    INVREQ, RETPAGE, TSIOERR, WRBRK. **PURGE MESSAGE** (https://www.ibm.com/docs/en/cics-ts/6.x?topic=summary-purge-message) "discontinues the building of a BMS logical message" and
    "deletes the current logical message, including any pages of device-dependent data stream already written to CICS temporary storage". Both
    belong to the ACCUM / PAGING message SEND MAP and SEND TEXT refuse: there is no message to complete or purge, and paging to a terminal
    operator (the page the operator views, RETPAGE) is a terminal dialogue the region does not run.
  - **CONVERSE** (terminal), **POST** and **WAIT EVENT** were refused here by #5185; they are modelled by X63 (#5079), which carries their IBM pages.
    WAIT EXTERNAL and WAITCICS stay name-only (X63).
- **A PIC X(4) byte view of the pointer (#6876).** A `PIC X(4)` item that a plain POINTER shares (either one REDEFINES the other) may be
  tested for equality with `X'FF000000'` (IBM's no-COMMAREA value). The port and the stub refuse ADDRESS COMMAREA at run time when EIBCALEN is 0,
  so no handle ever holds that value and the test is false wherever it runs; any other use of such a byte view stays a hole. 
  **A program that declares no `01 DFHCOMMAREA`** (#5079; the crucible's CAADDR, CAADSB, CAEBCA, CAEBSB, which ask CICS for the address with
  ADDRESS COMMAREA and never name the record): the harness translator (not the det translator) gives its LINKAGE SECTION a one-byte stand-in
  `01 DFHCOMMAREA PIC X(1)` and `USING DFHCOMMAREA`, so the stub passes the real COMMAREA. The pointer `GGCADDR` stores is that area's own
  address, whatever size the stand-in declares, so `SET ADDRESS OF view TO ptr` sees the caller's bytes (IBM: the pointer addresses "the
  communication area (COMMAREA) available to the currently executing program"). The stand-in is a harness device, not a claim about IBM's
  translator. Where the task has no COMMAREA (EIBCALEN 0) the command is refused at run time as above, so the crucible's `no-commarea` scenarios
  (both cases) are a named refusal, not a pass: IBM's answer there is X'FF000000', which the port cannot hold (the stub could, as for an unsized
  TWA; not modelled, to keep the two runtimes alike). Crucible `cobol-stub` cells: `ca-address-commarea` link-view and eib-view pass;
  `ca-address-eib-commarea` commarea-writethru passes. `eib-qiderr` fails on the case's own oracle, not the stub: the program moves `VE-RESP`
  (a live view of the EIB) to its report after a successful WRITEQ TS, which resets EIBRESP to 0, while the expected report says `RESP=0044`
  (a case defect to raise in cics-crucible; the breadcrumb written before the WRITEQ TS agrees). A case whose oracle expects QIDERR from a TD
  command but whose CSD defines no TDQUEUE now gets an empty `tdqueues.cfg` from the runner, so the stub answers QIDERR instead of taking every
  queue as defined.
- **Status:** ASSUMED where listed, REFUSED where IBM is silent. Reached by no corpus program yet (0 uses in the 18 corpora, #5079), so no
  port moves and no ZECS program is made whole by this entry. cics-crucible cases to add (separate queue items): ADDRESS EIB / COMMAREA with the
  EIB view reading EIBRESP after a command and a COMMAREA view written through; ADDRESS COMMAREA with no COMMAREA (refused).
