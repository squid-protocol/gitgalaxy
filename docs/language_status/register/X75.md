- **What IBM says** (CICS TS 6.x, https://www.ibm.com/docs/en/cics-ts/6.x?topic=summary-read and the other file control commands). FILE(filename) "specifies the name of the file to be accessed. The name must be alphanumeric, up to 8 characters long, padded with trailing blanks if necessary"; the condition FILENOTFOUND (RESP 12), RESP2 1: "The name referred to in the FILE option is not defined to CICS". A CSD file name (DEFINE FILE) is 1-8 characters with no blank in it.
- **Modelled.** The det translator passes a FILE / DATASET name with its trailing blanks dropped and its leading ones kept (`det/cics.py` `file_name`, `stripTrailing`; it used `strip`, which turned `'    FILE'` into `FILE`). `CicsTask.undefinableFile` is true for an empty name or one with a blank in it, and `CicsTask.fileFault` answers FILENOTFOUND for it after any planned condition (the stub's order: a planned fault first, then the name). The generated `store()` returns an empty store for such a name, so a command's eagerly evaluated arguments (a WRITE's key check) run first. The stub (`tests/equivalence/cics/ggcics*.c`) already answered FILENOTFOUND for any name its `files.cfg` lacks, trimming trailing blanks only.
- **What we assume.** (1) RESP2: IBM documents 1 and both sides answer 1 (row I of #6839, closed). (2) Which names the region defines is not known to the det port, so only names no CSD can hold are decided; a definable name without a store stays a `Hole` (not modelled).
- **Status:** ASSUMED. The oracle is GnuCOBOL plus our stub, not z/OS. Reached by zECS ZECS000 `control-record-first-write` (RETRIEVE answers NOTFND, ZF-TRANID stays blank, READ FILE('    FILE') answers FILENOTFOUND), which only ran on the det side once the harness handed it the scenario's stated control file (#6839 row A).
