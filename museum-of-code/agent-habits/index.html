GitGalaxy · A study of AI coding agents

Every Model Has a TellThree AI models built programs for the same ten jobs. The shape of their code kept giving them away.

We gave Claude Code (running two different models) and OpenAI's Codex identical jobs: a chess engine and a logic-puzzle solver, each in five languages, 60 programs in all. Then we ignored every name and every word of every comment, measured only the code's structure, and asked: can you still tell who wrote it?

By Joe Esquibel, with the GitGalaxy code-scanning engine · November 2026 · Everything on this page is interactive: tap, hover, pick.

Handwriting gives people away. A detective can match a ransom note to a suspect without reading a word of it, from the slant of the letters and the pressure of the pen. Code has handwriting too: how a program is cut into pieces, how long each piece runs, how many decisions it makes, which parts call which. Ignore what the names and comments say, and that shape is still there.

To find out whether AI coding agents have handwriting, we ran a controlled experiment. Three models built the same two programs, a chess engine that plays legal chess and a solver for logic puzzles called SAT, in C, Java, Python, Rust and COBOL. Each run started in a fresh, sealed container with the same written instructions and no human in the loop. An automatic judge with a hidden test set decided when a program was done.

Then we pointed GitGalaxy at the results. It reads source code the way an X-ray reads a skeleton: no running the program, no AI judge, just the structure.

How it works, in one paragraph. A job is one task in one language, such as "chess engine in Rust"; there are ten. For every program, GitGalaxy builds a shape profile: how many functions it has and how big they are, how many decisions each makes, which functions call which, and where comments sit (not what they say). Two profiles reduce to one shape difference: 0 means identical shape, and about 1 is typical for two programs written in different languages. Every comparison that matters below is made between programs doing the same job.

The short version
  • Our predictions weren't confirmed. We wrote down in advance that Claude would differ from Codex in five specific ways. After correcting for running several tests, none of the five passed; the closest missed by a hair.
  • But each model kept its handwriting. A model's second, independent round of programs looked like its first, and a program's closest look-alike came from the same model 83% of the time.
  • The habits belong to models, not companies. Sonnet and Haiku both run inside Claude Code, yet they differ from each other as much as either differs from Codex.
  • Language matters most. Changing a program's language moves its shape further than changing the model. That's why the model fingerprint only shows when you compare like with like.

Handwriting without a name

Here is the simplest possible test. Take any program, and line it up against every other program that did the same job. Which one has the most similar shape? If structure carried no trace of its author, the closest look-alike would come from the same model about as often as a blind pick.

A blind pick would land on the same model 27% of the time. The closest look-alike was the same model 43 times out of 52.

Two honest footnotes. This test was an afterthought, not one of the predictions we registered, so it needs repeating on fresh programs. And for Sonnet and Haiku, the closest look-alike was usually the model's own second round (34 of the 43 matches): this is mostly the "a model repeats itself" result seen from another angle. Codex ran once per job except in two, so only 4 Codex programs could be scored here (all 4 matched).

The prediction that wasn't confirmed

This study began with someone else's experiment. Mathieu Acher, a computer scientist at the University of Rennes, published pairs of programs that Claude Code and Codex built for the same tasks, with a human steering each one. When we scanned his pairs, the two agents looked different: Claude seemed to comment more, Codex seemed to bail out of functions early with return, and so on.

Looking at data and then announcing what you saw is how you fool yourself, so we did it the slow way. We wrote down five predictions and the exact test for each, published them with a timestamp, and only then ran 60 fresh programs that no prediction had seen. Each test counts the plain way: in how many of the ten jobs did the prediction point the right way? The last column is the chance of a result that strong by luck alone, corrected for running several tests at once.

The closest call was Codex's early exits (leaving a function early with return): they showed up in 9 of 10 jobs, and missed the bar by a hair. Nothing was refuted either. But the rows that did pass tell a different story from the one we went looking for. Haiku, the smaller Claude model, documents its functions far more than Codex and far more than its sibling Sonnet. Sonnet, meanwhile, reaches for while loops more than Haiku in every language that has them.

The habits didn't follow the company name on the box. They followed the model inside it.

What moves a program's shape

A fingerprint is only interesting if you know what else leaves marks. So we compared every pair of programs, about 1,700 of them, and sorted the pairs by what they had in common.

Read the chart top to bottom. Two runs of the same model on the same job sit close (median 0.32). Swap the model and the distance roughly doubles. Swap the task instead and it's about the same. Swap the language and the distance triples. A chess engine in COBOL and one in Python, written by the same model, have less in common than two Python chess engines by different models.

Language is the loudest accent. The model is the handwriting underneath it.

A model repeats itself

A fingerprint has to be stable to be useful. So Sonnet and Haiku each did the whole job twice, in two independent rounds, without any memory of the first. If the first round's style were a fluke, the second round would land anywhere.

Haiku's comment habit

One habit is visible without any scanner at all. Haiku writes comments, and in particular it puts a comment above its functions. It does this more than Sonnet in every one of the ten jobs, and more than Codex in every one of them too. Codex, in most jobs, writes almost none.

Be careful with what this means. It's not "Claude comments more": Sonnet and Haiku run in the same Claude Code tool and differ sharply. And it's about how much they comment and where, not what the comments say. A tool that sorts comments by meaning was right only about half the time on this code, so we didn't use it.

The clock

The agents also worked at very different speeds. Sonnet typically finished in under three minutes. Codex took about six. Haiku, the smaller and supposedly faster model, took around twenty. One Haiku run and one Codex run ran out the 60-minute clock.

What else GitGalaxy can now see

The registered tests are finished. But the same scans answer more questions, and these are where the next study starts. Everything in this section is exploratory: measured after the fact, each with its own comparison, and to be confirmed on fresh runs before anyone builds on it.

The scanner got caught too

Codex writes dense code, sometimes 2,000 characters on a single line. GitGalaxy has a safety rule that skips files that look minified, and it quietly skipped four of Codex's programs. We caught it by checking GitGalaxy's function counts against two independent tools (Tree-sitter and ctags), applied a rule we'd written down in advance, and fixed the scanner. Where GitGalaxy read a file, the three tools agreed almost function for function. The experiment didn't just use the instrument; it improved it.

What it can't tell you

  • Which agent is better. The judge was pass/fail. Nothing here ranks quality.
  • Anything beyond these models, tasks and languages. Ten jobs is small, and several results rest on one or two of them. The look-alike result was exploratory, not one of the registered predictions; it needs repeating on fresh runs and a new task.
  • What the comments say. We measure how much and where. Classifying comments by meaning was only right 54% of the time on this code.

How we know it's not luck

  • Written down first. Predictions, tests and the fingerprint of every analysis script were published before the confirmation runs; every later change is a dated note made before it was used.
  • Against chance. The look-alike result is compared with a shuffle test: relabelling the models at random never matched it in 2,000 tries.
  • Against itself. Each Claude model ran twice; a model's two rounds differ less than models do, and none of the registered habits differed between rounds.
  • Against other tools. GitGalaxy's function lists were checked against Tree-sitter and ctags on all 60 programs.
  • One instrument. Every number comes from one pinned version of GitGalaxy (commit 7d2e1f627).
